Framework case studies

Three real agent systems, read feature by feature as answers to the design questions from the earlier chapters.

How to read a framework

Take one feature. Deep Agents moves large tool results, over about 80,000 characters, into a file. The model sees only a short preview and the file's path. You could learn that as a setting to configure. But it is also an idea from chapter 4: keep large data outside the context, and let the model fetch the part it needs. This chapter reads real systems the second way, so each feature links back to the concept it implements.

Three systems get full profiles, because they make very different choices around the same loop. Hermes Agent is a long-lived personal assistant that edits its own notes and skills between conversations. Deep Agents is a library that wraps a standard loop in layers you can configure. Pi is a small core that leaves most features to extensions. Shorter profiles of other systems follow, and chapter 17b puts everything side by side.

Versions and evidence date

The facts on this page come from research notes checked on 2026-10-19. They hold for these versions:

  • Hermes Agent v0.22.2, released 2026-10-15.
  • Deep Agents: the deepagents Python SDK 0.7.28, released 2026-10-16.
  • Pi: @earendil-works/pi-coding-agent 1.3.0, released 2026-10-15.

These projects change quickly. For example, Deep Agents changed many defaults in 0.7.0 (2026-07-29), so older tutorials describe a different system. Docs also lag behind code. The Hermes loop docs still give a default turn limit of 500, but the v0.22.2 code has no limit at all.

Support levels

  • Built in Part of the system as shipped.
  • Optional Part of the system, but off until you turn it on.
  • Extension or custom Not in the core. An example extension, a plugin, or your own code adds it.
  • Not built in Absent. The project's answer is something else, such as plain files or an outside container.
  • Unknown The research did not establish it. Unknown does not mean unsupported.

Hermes Agent: an assistant that edits its own notes

Suppose you tell Hermes, in a Telegram chat, that you prefer short answers. The agent can save that preference to a small file, USER.md, right away. But the new line will not appear in the system prompt until your next session. Hermes builds the system prompt once per session, and changes it only when it compacts (summarizes) old history. So every request starts with the same text, and the provider's prompt cache can reuse its work (chapter 4).

Hermes Agent v0.22.2 is an open-source (MIT) application from Nous Research. The same agent core runs behind a CLI, a desktop app, an editor protocol, and an API server. A messaging gateway also connects it to 20+ chat platforms. You change most of its behavior in a configuration file, config.yaml.

What does this reduce to?

Hermes = one tool loop + a system prompt frozen per session + a session database.

Its learning = two small memory files + a skills folder + a review step that edits them after turns.

The fourteen questions

Core mental model
A personal assistant that lives on a server. One tool loop serves every chat front door, and between conversations the agent rewrites a notebook of memory, skills, and transcripts. Its design guide puts the cache first: "Per-conversation prompt caching is sacred." It also keeps the core small, so new abilities arrive as skills, plugins, or MCP servers.
What it calls an agent
A profile is the stored home of one assistant: its config, keys, memory, skills, and sessions. An agent is the running assistant that uses a profile. Subagents and the review step run the same agent class.
Loop Built in
Each user message starts one turn. Hermes calls the model, runs the tool calls it asks for, adds the results, and repeats until a reply contains no tool calls. Since v0.20.5 there is no step limit by default, because limits "caused silent mid-task truncation". Instead, a watchdog stops a turn after 600 seconds without progress, and guards warn when the same call keeps failing.
State Built in
During a turn, the state is a list of messages. Each profile also has one SQLite database that stores every session and message, with keyword search. Memory, skills, and the agent's identity are plain text files in the profile folder.
Context construction Built in
The system prompt has three parts, ordered from most to least stable. Identity and tool guidance come first, then project files such as AGENTS.md, then the skills list and memory. Anything that changes per call goes into the user message instead, so the cached prefix stays the same. When the conversation fills half the window (at least 75% for windows under 512K tokens), a second model summarizes the middle of the history. The old messages stay in the database, marked as compacted.
Tools Built in
Tools register themselves, and Hermes hides any tool whose key or binary is missing. Rarely used tools sit behind a search tool that loads their definitions on demand. In v0.22.0 that cut the desktop tool definitions from 13,367 to 6,883 tokens. The shell tool runs on 7 backends, from the local machine to Docker and remote sandbox services such as Modal.
Planning Built in
There is no separate planner. A todo_list tool keeps a task list and puts it back into the context after compaction. In v0.22.2 the model has to find it through tool search first. The /goal command adds an outer loop. After each turn, another model answers done, continue, or blocked. On continue, Hermes keeps going, for up to 20 turns by default.
Subagents Built in
delegate_task starts child agents that know nothing except the goal and the context the parent writes. They get fewer tools than the parent, for example no memory and no way to ask the user. By default they run in the background, up to 10 at once. Each result comes back later as a new message, with a summary of at most 24,000 characters.
Memory Built in
Two small files are always in the prompt: notes about the environment (2,200 characters) and about the user (1,375 characters). The agent writes them with a memory tool. A write over the limit fails, so the agent has to merge entries. Older conversations are found by keyword search over the session database, with no model call.
Skills Built in
A skill is a folder with a SKILL.md file. The prompt lists only skill names and descriptions, and the model loads a full skill when it needs one. The agent also writes and edits skills itself, and a curator archives unused agent-written skills after 30 days.
Permissions Built in
Hermes checks shell commands against 110 patterns for dangerous commands. By default, a second model reviews each match and approves it, denies it, or escalates it to you. A short hardcoded blocklist and your own deny rules apply even when approvals are off. In a container backend the approval check is skipped, because the container is the boundary.
Persistence Built in
Hermes saves every message during the turn, so a session survives crashes and restarts. File rollback is optional: Hermes can snapshot the working folder into a hidden git store before edits. Cron jobs run as fresh agents on a schedule.
Distinctive ideas
It improves itself through text, not training: a review step after turns edits the memory and skill files. It also offers a ladder of autonomy. You can run one turn, a judge-driven /goal loop, a cron schedule, or a Kanban board. The Kanban board is a shared task queue in SQLite that several agent processes work from.
Hidden complexity
Hermes hides provider differences (three API formats, sign-in, retries, fallbacks), cache management, compaction, and chat-platform plumbing. It also hides its own upkeep. You never have to ask it to remember, because counters trigger the review step for you.

What it teaches

  • Prompt caching can shape a whole context design. Hermes freezes the stable parts, puts the changing parts last, and delays prompt changes to the next session. See chapter 4.
  • A "self-improving" agent can be ordinary code. Counters decide when a review call runs, and that call edits text files. This is the memory write path from chapter 5, run automatically.
  • An approval gate can use a model as the approver. The gate is enforced in code, but its decisions are only as good as that model. See chapter 11.

Sources: the Hermes docs and the v0.22.2 code. Each row in chapter 17b links its exact source.

Deep Agents: a standard loop wrapped in layers

Suppose a custom search tool returns 200,000 characters. Deep Agents writes that result to a file. Only its first and last 5 lines, plus the file path, go into the conversation. The model can read more with its file tools if it needs to. The model did not ask for this. Middleware did it, meaning code that runs around every model call. Most of what Deep Agents adds works this way.

Deep Agents is LangChain's agent library. This profile covers the Python SDK, deepagents 0.7.28, which runs on langchain 1.4.6. Underneath is LangGraph, a LangChain library that stores the state of each run and can pause it. You call Deep Agents from your own code. A JavaScript version and a terminal coding agent, Deep Agents Code (dcode), ship as separate packages.

What does this reduce to?

Deep Agents = LangChain's standard loop + an ordered list of middleware + a task tool that runs child agents.

Its storage = one file interface over swappable backends + LangGraph checkpoints.

The fourteen questions

Core mental model
A standard tool loop wrapped in ordered middleware, with a virtual file system as working memory and subagents as throwaway context windows. It adds no new runtime. create_deep_agent() assembles the middleware and hands the loop to LangChain and LangGraph.
What it calls an agent
The agent is the compiled LangGraph graph that create_deep_agent() returns: a model, tools, and middleware, run as a loop. Subagents are agents too, and any LangGraph graph with a message list can serve as one.
Loop Built in
LangChain runs it: call the model, run every requested tool, and end when a reply contains no tool calls. Tool calls from one reply run in the same step. Deep Agents sets no turn limit of its own. It only sets LangGraph's recursion limit, to 9,999 steps.
State Built in
State is a typed dictionary that LangGraph keeps per conversation thread. Besides the messages, it can hold the files themselves. By default, files live in the state, not on disk.
Context construction Built in
Since 0.7.0 the SDK ships no general system prompt. The prompt is your own text, plus extra sections from a per-model profile for some models. Middleware adds the skills list and memory files on each call, and large tool results go to files, as in the example above. At 85% of the window, Deep Agents archives the oldest messages to a file and replaces them with a summary. The model sees the summary plus recent messages, while the state keeps every original message.
Tools Built in
It ships file tools (ls, read_file, write_file, edit_file, glob, grep, delete), a shell tool (execute), and task for subagents. execute appears only when the storage is a sandbox, so the default setup has no shell at all. You add your own tools as plain functions, and MCP tools through LangChain.
Planning Optional
A write_todos tool is opt-in since 0.7.0. LangChain removed it from the defaults after testing three models. The tool gave no significant accuracy gain, and cost went up on two of them. Even when it is on, nothing checks that the agent follows the list.
Subagents Built in
The task tool runs a child agent while the parent waits. The child starts with only the task description and returns only its final message. But with the default storage, the child reads and writes the same files as the parent. So its context is isolated, while its state is shared. The parent runs children in parallel by calling task several times in one reply.
Memory Optional
Short-term memory is the thread's saved state. Long-term memory is files stored outside any one thread. You route a folder such as /memories/ to a LangGraph store, scoped per user or per assistant. If you list an AGENTS.md file as memory, it goes into the prompt on every call. The agent edits it with the normal file tools.
Skills Optional
Skills use the Agent Skills format: a folder with a SKILL.md file. When you pass skill folders, the prompt lists each skill's name, description, and file path. The model reads the file with read_file when a task matches.
Permissions Optional
You name the tools that need approval with interrupt_on. The run pauses, and a person approves, edits, or rejects each gated call. You can also set allow, deny, or ask rules on file paths, but they cover only the built-in file tools, not the shell. The README puts it this way: "Enforce boundaries at the tool/sandbox level, not by expecting the model to self-police."
Persistence Optional
Persistence comes from LangGraph. A checkpointer is a store that saves the state after every step. If you pass one, a run can resume after a crash without redoing finished steps. It can also wait for an approval as long as needed. Files can live in the state, in a LangGraph store, on real disk, or in a sandbox.
Distinctive ideas
One file interface serves file tools, skills, memory, offloaded results, and archived history, so changing the storage changes all of them at once. The defaults also follow experiments: the long built-in prompt and the default todo tool were both removed after tests showed no gain.
Hidden complexity
It hides the order of about a dozen middleware, token counting, and history archiving. It also repairs tool calls that never got a result after an interrupt. LangGraph hides threads, checkpoints, and pausing.

What it teaches

  • Work that must happen on every call belongs in middleware, because a tool runs only when the model chooses it. See chapter 2.
  • Files work as overflow storage for context. Large outputs, old history, and memory all go to files that the model can read back. See chapter 4.
  • An isolated context does not mean isolated state. A child agent that shares the parent's files can overwrite them. See chapter 7.

Sources: the Deep Agents docs and the deepagents code read at release 0.7.28.

Pi: a small core you extend

Ask Pi to plan a large refactor. It has no plan mode and no to-do tool, so the plan goes into a file such as PLAN.md. You can read that file, edit it, and commit it with your code. Pi's creator prefers it that way, because file plans "can be shared across sessions, and can be versioned with your code". Much of Pi follows this pattern: a feature that other systems build in becomes a file, an extension, or a separate process.

Pi calls itself "a minimal, extensible agent harness that you can make your own". This profile covers @earendil-works/pi-coding-agent 1.3.0. Pi is both a CLI, pi, and a set of packages you can import. One package handles model access across providers, one runs the loop, and one is the coding agent. Mario Zechner created it, and Earendil acquired the project on 2026-04-08.

What does this reduce to?

Pi = one loop + four tools + a short system prompt + a session log stored as a tree + an extension API. Everything else is an extension, a file, or a separate process.

The fourteen questions

Core mental model
A tiny agent core with a large plugin system. The goal is control over context: its creator wrote that "Exactly controlling what goes into the model's context yields better outputs". So features stay out of the core, and Pi can write its own extensions and load them with /reload.
What it calls an agent
An Agent object holds the model, tools, and messages, and an AgentSession wraps it with queued messages, compaction, and extensions. Pi's words differ from this course: a Pi "turn" is one model reply plus its tool calls, which chapter 1 calls a step.
Loop Built in
Pi streams a reply, runs its tool calls in parallel, records the results, and repeats while tool calls or queued user messages remain. You can steer mid-run: a message you type while Pi works is delivered after the current tool calls finish. A search of the source found no step limit.
State Built in
Each session is one append-only JSONL file. Every entry points to its parent entry, so the entries form a tree, and you can branch from any point. Even changes to the system prompt and the tool list are entries, so any branch can be replayed exactly.
Context construction Built in
The system prompt is short: roughly 1,000 to 1,500 tokens with tool definitions, by a character-count estimate. Project instruction files (AGENTS.md) load from a global folder and every parent directory. When the context nears the window limit, minus a reserve of 16,384 tokens, a model call summarizes older entries. Pi keeps about the last 20,000 tokens word for word, and the original entries stay in the file.
Tools Built in
Four tools by default: read, bash, edit, and write. The creator's reason is that models already know bash and "have been trained on the read, write, and edit tools with similar input schemas". Pi cuts long output at 2,000 lines or 50 KB, and bash saves the full text to a temp file. MCP is built in since 0.99.0, but MCP tools stay hidden until the model searches for them or calls them from a script.
Planning Extension or custom
No plan mode and no to-do tool, by design. The creator wrote that "to-do lists generally confuse models more than they help". Plans live in files, and a plan-mode extension ships as an example.
Subagents Extension or custom
Not built in. The creator calls built-in subagents "a black box within a black box". Instead, he suggests asking Pi to run another copy of itself through bash. An example extension runs each subagent as a separate pi process with its own model, tools, and prompt.
Memory Not built in
There is no memory system. What carries over between sessions is ordinary: session files you can resume, AGENTS.md files, files the agent writes, and skills.
Skills Built in
Pi follows the Agent Skills format. The prompt lists each skill's name, description, and file path. When a task matches, the model reads the SKILL.md file with the normal read tool. Skills in the project's .pi/skills/ folder load only after you trust the project.
Permissions Extension or custom
There is no permission system, and Pi does not ask before tool calls. Its creator calls this "YOLO by default", and the docs recommend running Pi in a container or VM. The only built-in prompt asks whether to trust a project's own settings and extensions. Extensions can block or change any tool call, and if such a handler crashes, Pi blocks the call.
Persistence Built in
Pi saves every session automatically, and you can resume it, branch it, or fork it into a new file. Branching rewinds the conversation but not the files on disk, so an example extension uses git to restore them. Resuming a turn that crashed is the goal of Pi Durable, an experimental separate package.
Distinctive ideas
The agent extends itself: extensions are TypeScript files that load without a build step, and Pi writes many of them. Codemode lets the model write a JavaScript script that calls tools. The script runs inside QuickJS, a small JavaScript engine with no file or network access, so only its output enters the context.
Hidden complexity, and what it leaves to you
Pi hides provider differences, compaction, session-tree bookkeeping, and parallel tool scheduling. It leaves the rest to you: the sandbox, approval rules, planning, subagents, and memory.

What it teaches

  • Every tool definition costs context on every call. In 2025 Pi's creator measured one browser MCP server at 21 tools and 13.7k tokens. Pi's MCP support still hides those tools by default. See chapter 4.
  • An append-only log makes state easy to replay and branch, because nothing is overwritten. See chapter 3.
  • When a system has no built-in gates, the security boundary has to come from outside, such as a container or VM. See chapter 10.

Sources: the Pi code and docs at release 1.3.0, and its creator's design post (2025-11-30).

Other systems, briefly

Claude Code: advice versus enforcement

Claude Code is Anthropic's coding agent. Its project file, CLAUDE.md, loads every session, but the docs call those instructions advisory, while hooks are deterministic. A hook is a script that the runtime runs at a fixed point. For example, a Stop hook can keep a turn from ending until a check passes. That is the difference between an instruction and an enforced gate from chapter 10.

Its sandbox shows what containment buys. Claude Code users approve 93% of permission prompts, which Anthropic calls "approval fatigue". Anthropic added an OS sandbox, using bubblewrap on Linux and Seatbelt on macOS. A proxy outside it lets traffic reach only approved domains. In internal use, this cut permission prompts by 84%, because a command that cannot reach much needs less review.

Sources: the Claude Code best practices docs page and Anthropic's sandboxing post (2025-10-20), both checked 2026-10-19.

LangGraph: the runtime under a harness

Deep Agents leaves saving and pausing to LangGraph. LangChain describes its stack in three layers: LangGraph is the runtime, create_agent is the framework, and a harness such as Deep Agents sits on top. Its list of harnesses also names the Claude Agent SDK. With a checkpointer, LangGraph saves every step of a thread. A run can then resume after a crash, or wait for a person as long as needed. A store holds data across threads. This is the durable execution from chapter 12, offered as a separate layer that a harness can build on.

Sources: LangChain's products page and LangGraph persistence docs, checked 2026-10-19.

Shared formats and protocols

Some pieces now work across systems. AGENTS.md is an open format for project instructions, "used by over 60k open-source projects", and all three profiled systems can read it. In the A2A project's words, "MCP standardizes agent-to-tool communication; A2A standardizes agent-to-agent communication." Neither is an agent loop. The MCP spec also says it "cannot enforce these security principles at the protocol level", so the host program has to enforce them.

Sources: agents.md, the MCP specification (version 2026-07-28), and the A2A specification (v1.0), checked 2026-10-19.

OpenHands, the OpenAI Agents SDK, PydanticAI, and smolagents build on the same primitives: a loop, tools, state, and per-call context. The course's research did not verify their details, so read them yourself with the same fourteen questions.

Check yourself

Hermes saves a memory entry in the middle of a session. When does the entry first appear in the system prompt, and why? (Q7)

Answer

At the start of the next session. The memory files go into the system prompt once per session, and changing the prompt mid-session would break the prompt cache. The file on disk changes right away.

A Deep Agents subagent runs with the default settings. What does it share with its parent? (Q12)

  1. Nothing at all
  2. The parent's full conversation
  3. The files, but not the conversation
Answer

The child's conversation starts with only the task description. But with the default storage, parent and child read and write the same files, and the child's changes stay after it ends.

You build Patch on Pi. Where does the security boundary come from? (Q23)

  1. Pi's built-in permission prompts
  2. A container or VM you run Pi in, with gates written as extensions as an extra layer
  3. Rules written in AGENTS.md
Answer

Pi has no permission system, and its docs say that watching the transcript does not create a boundary. An extension gate only covers the tool calls it intercepts, so containment has to come from outside.

Takeaways

  • All three run the same loop, and they load skills and compact history in similar ways.
  • They differ most in defaults. Hermes builds in memory, subagents, and approvals. Deep Agents builds in subagents and makes memory and approvals options. Pi leaves all three to extensions, plain files, and outside containers.
  • Framework facts expire quickly, so note the version and trust the code over the docs.
