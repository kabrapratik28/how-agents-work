Agent communication

Agents pass information through ordinary channels such as return values, queues, and databases. A model can act only on the part that reaches its context.

Two layers: coordination and context

Two coding agents work in the same repository. Before one edits auth/session.py, it must make sure the other is not editing that file. Later, a reviewer agent must tell the coder that a test still fails.

These are two different kinds of communication. The first is coordination: who works on what, who owns a file, whether a task is done. Your code handles it with locks, queues, and status fields, and none of it needs to reach a model. The second is information a model must act on, such as the failing test. That has to enter the coder's context, because a model sees nothing else (chapter 4).

Agent A's code→ Channel: queue, file, or table→ Agent B's code→ The part B's model needs

Everything that enters a context costs tokens and attention. It can also carry instructions, because a model treats all of its input as guidance. So send a reference instead of the content when you can: a file path, a task id, or a commit hash. For example, a research agent can save 40 KB of notes to /work/research/auth.md. Then it returns one line: "Three likely causes, details in /work/research/auth.md." The parent's context grows by one line instead of 40 KB. Anthropic's multi-agent research system works this way: its subagents store their outputs elsewhere and pass back lightweight references.

Systems analogy

Agents communicate the way processes do: through return values, shared memory, messages, publish and subscribe, job queues, and shared databases. The usual tradeoffs carry over.

Where it breaks: the final reader is a model. Everything you deliver to it costs tokens and can steer it. And a message in plain language has no fixed format, so the receiver can misread it.

Parent and child: return values

A coding agent needs to know where expired tokens are accepted. It hands the question to a subagent, which searches the code in its own loop and returns five lines.

result = delegate(
    "Find where expired tokens are accepted. "
    "Return at most 5 lines: file:line and one sentence each.",
    tools=["search_files", "read_file"],
)
# only `result` enters the parent's context

This is the simplest channel. The parent calls the child like a function, and the child's answer comes back as one tool result. It fits tree-shaped work with a clear question and a short answer. Most subagent designs start here (chapter 7).

The costs follow from that shape. The parent waits for the answer, or checks back later if the child runs in the background. Anything the child leaves out is lost. And a long answer floods the parent's context. So ask for a fixed format and a length limit, and put details in a file.

Real systems keep both directions narrow. In Deep Agents (0.7.28), the parent receives only the child's last message. In Hermes (v0.22.2), a child starts with no history from the parent, so the brief the parent writes is all it knows.

Not everyone agrees that a short answer is enough. Cognition argues: "Share context, and share full agent traces, not just individual messages". Its reason: actions carry implicit decisions, and agents that cannot see each other's decisions make conflicting ones.

Shared state

A research subagent writes notes.md into a set of files that it shares with its parent. The parent reads the file later, and only if it needs the details.

Here several agents read and write the same state inside one program. It might be a dictionary, a todo list, or a set of files. Nothing enters a context until an agent reads it, which keeps contexts small.

The risk is hidden coupling: any agent can change something another depends on, and nobody is told. Agents that write at the same moment can also overwrite each other. So you need a merge rule, often called a reducer, that says how two writes combine:

def merge_findings(old, new):        # a reducer for writes that arrive together
    return old + [f for f in new if f not in old]

state = {"findings": [], "files": {}}   # one object, shared by parent and children

Shared state fits agents that run in one program, in one run, with few writers.

How real systems do it

  • Deep Agents (0.7.28) isolates a subagent's context but not its state. With the default setup, children read and write the parent's files, and those files remain after the children finish. If subagents running in parallel write the same custom field, it needs a reducer, or the step fails.

Messages

A reviewer agent sends the coder a message: the test still fails, and the details are in a file.

{"from": "reviewer", "to": "coder", "re": "task-412",
 "kind": "change_request",
 "note": "test_login_expired_token still fails",
 "ref": "/work/review/412.md"}

With messages, one agent writes to another agent's inbox. The receiver's code decides when each message enters its model's context. Usually it arrives as a new message on the next turn. Messages fit a few long-lived agents that go back and forth. A review loop is one example, and a person steering an agent while it runs is another.

Every message enters a context, so chatty agents get expensive, and two agents can keep replying to each other forever. Treat each message as untrusted input, too. If the sender read a hostile web page, its message can pass the attack along. Give messages fixed fields, and keep the free text short.

Real systems draw this line in different places. With an extension, one Pi (1.3.0) agent can send prompts to another. Hermes (v0.22.2) keeps its model from messaging other chats on its own: its send_message tool is deliberately not offered to the model.

Event bus

The build system announces that a build failed. A triage agent starts a run, and a notifier posts in the team chat. The build system does not know that either of them exists.

bus.publish("build.failed", {
    "repo": "web-api", "commit": "9f2c1e7",
    "log": "ci/runs/5512/log.txt",          # a reference, not the log itself
    "event_id": "evt-77a1",                  # so repeats can be spotted
})
# subscribers: a triage agent starts a run; a notifier posts in chat

That is an event bus, also called publish and subscribe. A component publishes an event on a topic, and every subscriber to that topic reacts. You can add a subscriber without changing the publisher, so a bus suits triggers that start event-driven agents (chapter 1).

The costs are in tracing and delivery. When one event starts three reactions and one of them publishes more events, it gets hard to answer "what started this run?". Many buses can deliver an event twice, so subscribers check event ids. And an agent that reacts to its own events can trigger itself in a loop. To prevent that, give each event an id that links it to its cause, and count the hops.

Events should carry facts and references, not instructions. "Build 5512 failed, log at this path" is data, while "please fix the build" is a prompt hidden in an event.

Task queue

A planner agent adds task 7 to a queue. A research worker claims it, writes the answer onto the task, and marks it done. The planner sees that task 7 is done and plans the next step.

{"id": 7, "kind": "research", "status": "ready",
 "ask": "Which auth tests touch token expiry?",
 "parent": 3, "result": null}

In a task queue, the message is the task record itself: the request, its status, who owns it, and the result. Anyone can look at the board, including a person, who can also change a task. And a task survives when its worker crashes, because a lease hands it to another worker (chapter 12).

A queue fits work that must survive crashes, many workers, retries, and people who need to watch or steer. The costs are slower handoffs, more moving parts, and tasks that can run more than once.

How real systems do it

  • Hermes (v0.22.2) offers both channels and names the difference: "delegate_task is a function call; Kanban is a work queue where every handoff is a row any profile (or human) can see and edit". Its docs call Kanban comments "the inter-agent protocol": a worker that restarts reads the whole comment thread.

Blackboard

Three specialist agents debug the failing login test together. They share one board with sections for symptoms, possible causes, evidence, and ideas already ruled out.

board = {
    "symptoms":   ["expired tokens still accepted",
                   "test_login_expired_token: 200 != 401"],
    "hypotheses": [
        {"id": "h1", "by": "code", "text": "10-minute grace period in auth/session.py"},
        {"id": "h2", "by": "logs", "text": "token cache serves stale entries"},
    ],
    "evidence":   [{"for": "h1", "by": "test", "ref": "runs/882/test.log"}],
    "ruled_out":  ["clock skew on the test runner"],
}
next_agent = controller.pick(board)     # a set of rules, or a model call

This is the blackboard architecture, an old idea from AI research. Specialists watch the board and add to it whenever they can help. A controller decides who acts next, based on what the board says. Here, the controller might see that h2 has no evidence yet and wake the test agent.

A blackboard differs from plain shared state in two ways. The board is organized like the problem, and nobody fixes the order of work in advance. It fits problems such as diagnosis, where the next step depends on what the specialists have found so far.

The board grows as agents add to it. So give each agent only the sections it needs, and remove entries that are no longer true.

What does this reduce to?

Blackboard = a shared document with sections + specialists who add to it + a controller that picks who works next.

Database

Two coding agents must never edit the same file at once. Each one claims a file by inserting a row into a table. The database refuses a second row for the same file:

-- one row per file being edited; a second claim fails
CREATE TABLE claims (path TEXT PRIMARY KEY, agent TEXT, run_id TEXT);
INSERT INTO claims VALUES ('auth/session.py', 'coder-2', 'run-77');

The second agent's insert fails, and its code tells the model "file taken". The rule never had to appear in a prompt, so no wording can get around it.

A database is shared state that lives outside any program. It survives crashes, many programs and runs can use it, and transactions and constraints keep its data consistent. Each agent can query exactly the rows it needs, which keeps its context small. A database fits long-lived systems with many processes, and work that needs an audit trail.

Do not let models write raw SQL against shared tables. Wrap the database in narrow tools such as claim_file and get_task.

Tradeoffs

Each channel trades the same six properties. Coupling is how much each side depends on the other. Consistency is whether every agent sees the same data. Observability is how easily you can see what happened. The other three are how failures are handled, how much enters a context, and whether things arrive in order.

A sensible order to try them:

  • Start with return values.
  • Add files in a shared workspace when answers get large, and return the paths.
  • Move to a task queue when work must survive crashes or be visible to people.
  • Use an event bus for triggers, not for conversations.
  • Use a database when many processes share facts that need rules.
  • Use a blackboard when several specialists must build one picture in an order you cannot plan.

Protocols: MCP and A2A

Say Patch should use the team's ticket system, which runs an MCP server. Patch's code asks the server which tools it offers, shows them to the model, and forwards the model's requests to the server.

MCP, the Model Context Protocol, connects an agent's code to tools, data, and prompts offered by another program (chapter 2). It standardizes how tools are listed and called. It is not an agent loop, because your code still runs the loop and decides what executes. It is not a security boundary either. The server's tools run with the server's access, and their results are untrusted text in your context. The spec itself says MCP "cannot enforce these security principles at the protocol level", so your code must.

An agent can also sit on the server side. Hermes (v0.22.2) offers hermes mcp serve, which lets other agents reach its chat conversations through MCP.

A2A, the Agent2Agent protocol (version 1.0), covers the other pairing. In its own words, "MCP standardizes agent-to-tool communication; A2A standardizes agent-to-agent communication." Each agent publishes an Agent Card, a JSON document that lists its skills, its address, and how to sign in. Work travels as a Task with an id and a lifecycle, much like a record in the task queue above, and long tasks report progress by polling, streaming, or webhooks. The agents do not need to share their memory, tools, or internal logic with each other.

Other protocols connect agents to editors. Hermes runs an ACP server for editors such as VS Code and Zed. Deep Agents can be exposed to editors over the Agent Client Protocol. None of these protocols decides what enters a context or who may do what. Those decisions stay with you.

Running example: Patch talks through files

Patch's subagents already return short reports (chapter 7). Now the runtime saves each full report in a shared workspace and gives the parent only the summary and the file path. The reviewer's brief also carries paths to the diff and the test output instead of pasted copies. The subagents stay read-only, because the runtime does all the writing.

# Patch v12: reports and briefs carry full contents
- report = delegate(explorer, task)
- review = delegate(reviewer, brief + diff_text + test_output)
# Patch v13: summaries and paths in context, contents on disk
+ report = delegate(explorer, task, format="summary first, at most 5 lines")
+ path = workspace.save(f"explore/{task.issue}.md", report.full)   # the runtime writes
+ parent.add(tool_result(report.summary + "\nFull notes: " + path))
+ review = delegate(reviewer, brief + "Diff: /work/412.diff  Tests: /work/412-tests.txt")

What goes wrong

The parent's context floods

Why it happens
A child returns its whole transcript or a huge result, which buries the parent's earlier instructions.
How to spot it
Track the size of each tool result, and watch for jumps right after a delegation.
What to do
Set a length limit and a format for answers, and return file paths instead of contents.

Two agents overwrite each other

Why it happens
They share files or state, write at the same moment, and nobody owns anything.
How to spot it
Lost changes, merge conflicts, or reducer errors.
What to do
Give each file or field one writer, use claims the database enforces, or give each agent its own copy of the repository.

An attack travels between agents

Why it happens
A research agent reads a hostile page and passes its demand along in a message. The next agent treats it as a request.
How to spot it
Agent messages contain instructions that no user gave.
What to do
Treat other agents' output as data, give messages fixed fields, and enforce permissions in every agent's code (chapter 10).

You decide, AI builds

Decide yourself

  • Which channel each pair of components uses, and why.
  • What enters each model's context, in what format, and how big it may get.
  • Who owns each file, record, and field, and how conflicts are settled.
  • Which messages count as requests, and which are only data.

Delegate to AI

  • Queue, bus, and database plumbing.
  • Message formats and validation.
  • Ids that link events to their causes, and logs across agents.
  • Connections to MCP servers and other protocols.

Check yourself

How do agents communicate? (Q26)

Answer

Through ordinary channels: return values, shared state, messages, an event bus, a task queue, a blackboard, or a database. Coordination such as claims and task status stays in code. Information a model must act on has to enter its context, so good designs send references and keep answers short.

A subagent produced 30 KB of notes. What should the parent receive?

  1. All 30 KB, so nothing is lost
  2. A short summary with evidence, plus the path to the full notes
  3. Nothing. The parent can search the workspace later.
Answer

A short summary plus a path. The parent's context stays small, and the details are one read away. With nothing returned, the parent does not even know the notes exist.

Two agents must never edit the same file at once. Where should that rule live?

  1. In both agents' system prompts
  2. In a claim that your code or the database enforces, such as a unique key
  3. In a message each agent sends before editing
Answer

In an enforced claim. A prompt is a request that a model can ignore, and a message announces a plan but stops nothing. A unique key refuses the second claim, whatever the models say.

Takeaways

  • Keep claims, locks, and task status in your code or your database, where rules are enforced, not in prompts.
  • Choose a channel by what must survive and who must see it. Use return values for short answers, files for details, a queue for durable work, and a database for shared facts.
  • Protocols such as MCP standardize how agents and tools connect, but not what enters a context or who may do what.
