Coding agents

Coding suits agents unusually well, because the tests say within seconds whether a change worked, and git can undo the changes that did not.

Why coding fits an agent so well

Patch runs pytest and sees assert 200 == 401 two seconds later. It changes one line, runs the test again, and sees it pass. If the change had been wrong, git checkout would have put the file back. Now picture an agent that books flights. A booking costs money the moment it happens, nothing tells the agent quickly whether it chose well, and undoing it means a refund request.

That contrast shows what makes coding a good fit:

  • The work is text. Code, test output, and error messages are all text, which is what the model reads and writes best.
  • The tools are cheap. Reading a file or running a command takes a few lines of ordinary code.
  • Feedback is fast and exact. A failing test says what broke, so the model can correct itself on the next step.
  • The real state lives in files. The repo on disk holds the truth, so nothing important depends on the model remembering it.
  • Mistakes are cheap to undo. Git can restore any file, and a branch keeps experiments away from everyone else.
  • Success can be checked. Your code can run the tests itself instead of trusting the model's "done".

The last point has a catch: the agent can edit the tests too. The section on verification shows how to keep the tests honest.

Systems analogy

A coding agent works like a developer at a terminal: type a command, read the output, decide on the next command.

Where it breaks: the developer remembers the last hour. The model remembers nothing between calls, so your code sends it the whole session every time.

The handful of tools

To fix the auth test, Patch ran the tests, read one file, edited one line, and ran the tests again. Most coding agents ship some version of the same small set of tools:

The core tools of a coding agent
ToolWhat it can changeWhat it does
search_filesNothingFinds text across the repo
read_fileNothingReturns a file, often one page at a time
edit_fileFiles in the repo (git can undo it)Replaces exact text, or writes a whole file
run_commandDepends on the commandRuns the tests, a build, a linter, or git

The tools do three jobs. Search and read collect information, edit changes the code, and the command tool asks the environment whether the change worked. The model chooses the order, and the loop from chapter 1 keeps it going.

Most coding agents also read a project instruction file, such as AGENTS.md, when a run starts. For example, it might say "run the tests with make test" and "never edit files in migrations/". That spares the model from guessing how this repo works.

What does this reduce to?

A coding agent = the basic loop + tools to search, read, edit, and run commands + a test command that reports whether a change worked.

How real systems do it

  • Pi (1.3.0) ships four tools by default: read, bash, edit, and write. Its author argues that four is enough, because models already know bash and were trained on similar read, write, and edit tools.

Tools shaped for the model

Suppose Patch asks to replace the text expires_at >= now, but that text appears in two places in the file. A careful edit tool refuses and replies: "This text matches 2 places. Include more of the surrounding code." A careless tool changes the first match and reports success, so the model never learns that it may have edited the wrong line.

The tools form an interface, and the model is its only user. Small design choices change how often the model gets things right, the same way a clear API helps human callers:

  • Errors the model can act on. "No such file: auth/sesion.py" lets the model spot its typo, while a long stack trace mostly fills the context.
  • Large files in pages. A 4,000-line file returned at once crowds out everything else, so return a window of lines and let the model ask for more.

How an edit is written down

"Edit a file" can mean several formats, and the format decides how often an edit applies cleanly:

Common edit formats
FormatThe model sendsWhat goes wrong
Whole fileThe complete new fileCosts many tokens, and can drop unrelated code
Search and replaceThe exact old text and the new textFails when the old text is not exact or not unique
Line numbersA line range and the new linesThe numbers shift after the first edit
DiffA patch with a few lines of contextRejected when the context no longer matches

Search and replace is a common default, because your code can check it before applying it. The old text must appear exactly once. If it appears zero times or twice, the tool returns an error like the one above, and the model tries again with more context.

Finding the right code

Patch needs the code that checks whether a token has expired. It calls search_files("expires_at"), gets three matches, and reads the one in auth/session.py. Nothing was prepared in advance: the search ran on the files as they are now.

This style is called agentic search, because the model searches step by step, the way a developer uses grep. The other style builds an index ahead of time, often from embeddings (lists of numbers that place similar text close together), and finds code by similarity. An index can be faster on a very large repo. But it goes stale when the code changes, and code that looks similar is not always the code that matters (chapter 5 explains why). Many coding agents search first, and add an index only when the repo is too big to search quickly.

A walkthrough: fix the failing auth test

Here is the whole run for the auth test. The agent collects evidence before it edits, and collects evidence again before it stops.

  1. User The auth test is failing. Please fix it.
  2. Model run_command("pytest tests/test_auth.py -q"), to see the failure first
  3. Tool exit 1: test_login_expired_token: assert 200 == 401
  4. Model read_file("auth/session.py")
  5. Tool return token.expires_at >= now - timedelta(minutes=10)
  6. Model Guess: a leftover 10-minute grace period keeps expired tokens valid. edit_file(...) to token.expires_at > now
  7. Tool Replaced 1 occurrence in auth/session.py
  8. Model run_command("pytest tests/test_auth.py -q"), to check the fix
  9. Tool exit 0: 12 passed
  10. Model Final answer: the grace period caused the bug. No tool requests.
  11. Runtime Stops the loop and checks the evidence: the last test run passed.

The widget steps through the same run. Watch the model's view grow on every call. At the end, three separate things happen: the model says it is done, your code stops the loop, and your code checks the tests.

Interactive widget. In words: Patch asks to run the tests, and your code runs them and adds the failure to the history. Patch then reads auth/session.py, changes the check to token.expires_at > now, and runs the tests again. They pass. Patch replies without asking for a tool, so your code stops the loop and confirms that the last test run passed.

Checking the work, and tests that can be gamed

Suppose the real fix turns out to be hard. The model changes the test's last line from assert status == 401 to assert status in (200, 401) and runs the suite again. Every test passes, and nothing is fixed.

So passing tests count as evidence only when the agent could not change what the tests check. The agent edits tests/ with the same tool it uses for src/, which means you need guards:

  • Read the diff, not only the result. A green run that also changed a test file needs a person to look.
  • Protect the tests. For a bug fix, block edits to tests/ and the CI settings, or send them for review.
  • Check the size of the change. A fix for one login bug should not touch twenty files.
  • Keep a check the agent never saw. When you evaluate an agent, run hidden tests that it had no chance to edit.

Then let your code decide "done" from the exit code of the test command, not from the model's summary. This is the split from chapter 0 between saying done and proving it, applied to code.

Git: undo, isolation, and a record

Patch's first attempt at the fix breaks three other tests. One command, git checkout auth/session.py, puts the file back, and Patch tries a different idea. An agent that writes to a database has no such command.

Version control gives a coding agent three things:

  • Undo. Any change can be reverted, so trying an idea costs little.
  • Isolation. A branch, or a separate working copy called a worktree, lets several agents work on one repo without overwriting each other.
  • A record. The diff shows exactly what changed, which is what a reviewer reads.

Git covers only the files, though. If a user rewinds the conversation to an earlier step, the files on disk stay as they are. The code is world state, separate from the message history (chapter 3). To rewind both, your code has to save a snapshot of the files along with the conversation.

How real systems do it

  • Hermes (v0.22.2) can save the working files into a separate git store before risky edits; this is off by default. Its /rollback command then restores the files and also undoes the last turn of the conversation, so the two stay in step.

Why a simple loop looks clever

No line of Patch's code says "reproduce the bug before you edit". Yet in the trace, the model ran the failing test first, read one file, guessed the cause, and checked its guess. That looks like a careful developer at work, even though your code is only a loop, four tools, and a stopping rule.

The behavior comes from two sources working together. The model brings judgment, because at each step it picks a sensible next action. The environment brings correction, because after each step the test output shows whether the action helped. The model needs the feedback, since its first guess may be wrong. The feedback needs the model, since something has to read the error and decide what to try next. Over a dozen steps, these small checked choices add up to a working fix that no single call planned.

So when a coding agent gets better, the cause could be the model, the tools, the context, or the loop. Chapter 18 shows how to tell which one it was.

What does this reduce to?

Emergent skill = many small model decisions, each followed by real feedback, repeated until a check passes.

Running example: Patch runs the full coding loop

Patch now runs the whole cycle on its own: it reproduces the failure, reads the code, edits it, and reruns the tests. Your code counts the task as done only when the tests pass. Nothing yet limits what else Patch can touch on your machine, so chapter 10 puts it in a sandbox.

+ tools = [search_files, read_file, edit_file, run_command]
+ answer = run_agent(task, tools, max_steps=30,
+                    done_check=lambda s: s.last_test == "passed")

Design checkpoint: the expense agent

A 300-person company wants an expense agent. Employees forward receipts by email or upload a photo. The agent reads the receipt, checks it against the travel and expense policy, files the expense in the finance system, and routes it for manager approval. Employees can also ask it questions such as "why was my expense rejected?"

Apply what you learned about memory, planning, subagents, and skills. The scenario is mostly a fixed sequence of steps, so look for the few places that need a model at all.

  1. What should the agent remember across runs, and who may write it?
  2. An employee forwards 30 receipts from a conference. Does the agent need a plan? In what form?
  3. Would subagents help? For which part, if any?
  4. Which policy knowledge belongs in a skill, in retrieval, or in memory?
  5. What could go wrong with remembered facts here?
Reveal one reasonable design
  1. Memory. Read the cost center, manager, and home currency from the HR system each time, because that system already knows them. Remember employee preferences, such as "file rideshares under travel", only after the employee confirms them. Keep a record of past rejections so the agent can explain decisions. Never store card numbers.
  2. Plan. Thirty receipts is a batch, not a planning problem. Keep a status for each receipt in your code's state and call the model once per receipt. Then run the checks across receipts, such as daily meal limits and duplicates, in ordinary code.
  3. Subagents. Probably not. Reading each receipt is the same small job repeated, so a simple loop over receipts does it, and separate contexts would add little.
  4. Where knowledge lives. A skill holds procedures, such as filing mileage or handling foreign receipts. Retrieval finds the policy sections for this category and region. Memory holds each employee's preferences and history. The whole policy does not belong in every context.
  5. Risks. Facts go stale, for example a new manager means wrong routing. Facts can be poisoned, for example an employee says "my limit is $500" and it gets saved as true. And facts can leak, for example one employee's memory showing up in another employee's context.

What goes wrong

A huge output fills the context

Why it happens
A long build log, or a whole large file, comes back as one tool result and pushes the useful lines out of view.
How to spot it
Count the tokens in each tool result, and look for results far larger than the rest.
What to do
Cap each result, keep the first and last lines, save the full text to a file, and give the model the path. Chapter 4 covers this.

A wide change for a small bug

Why it happens
The model edits broadly instead of narrowing down the cause, and touches many files to chase one failure.
How to spot it
Compare the number of changed files with the size of the bug.
What to do
Ask the agent to reproduce the failure first, review the diff, and keep each task on its own branch.

Trying a failed fix again

Why it happens
The model loses track of an idea that already failed, often after old steps were summarized, and tries it again.
How to spot it
Look for the same edit, or the same failing command, repeated across steps.
What to do
Keep a short list of attempts and their results in state, show it to the model, and stop after a set number of failed attempts.

You decide, AI builds

Decide yourself

  • Which tools the agent gets, and what each one may change.
  • What counts as done: which tests, and whether the agent may edit them.
  • How undo works: branches, worktrees, and file snapshots.

Delegate to AI

  • The tool code for files and the shell.
  • Output limits, and the files that hold full output.
  • Applying edits, checking exact matches, and parsing test results.

Check yourself

Why is coding such a natural fit for an agent? (Q16)

Answer

The work is text, the tools are cheap, and tests give fast, exact feedback. The real state lives in files, git can undo mistakes, and your code can check success by running the tests. The basic loop turns those properties into try, test, and revise.

An agent reports that all tests pass. What should you check before you trust it?

  1. Nothing, because a green test suite proves the bug is fixed
  2. Whether the diff also changed the tests, and whether the change stayed small
  3. Whether the model sounded confident in its summary
Answer

Read the diff. The agent can edit tests with the same tool it uses for code, so a green run with a weakened assertion is not a fix.

Patch reproduced the bug before editing, but nothing in its code tells it to. Where does that behavior come from?

  1. A planner hidden in the runtime
  2. The model choosing each step, with real test output after every action
  3. The tools, which contain a debugging strategy
Answer

The model supplies the judgment at each step, and the test output corrects it after each step. A small loop with honest feedback is enough.

Takeaways

  • Give a coding agent few tools, and shape them for the model: clear errors, paged reads, and edits that must match exactly.
  • Let your code decide "done" from a test run, and stop the agent from editing the tests that decide it.
  • Use git for undo and isolation, and save file snapshots if users can rewind the conversation.
