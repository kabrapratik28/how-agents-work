LLM vs agent

The model only turns context into a response. Everything that makes it an agent is ordinary code around it.

The model is a function

Start with the smallest useful picture. For design purposes, a language model is a function.

response = model(context)

The context is a sequence of tokens. It holds instructions, conversation, documents, and descriptions of available tools. The response is more tokens. Usually that means text. Sometimes it is a structured request, such as "call search_files with these arguments".

Four properties of this function shape everything else in the course.

  • It runs no code. It cannot open a file, call an API, or run a command. It can only produce text that asks for those things.
  • It keeps nothing between calls. Each call starts from the context it receives and nothing else.
  • It is not fully predictable. The same context can produce different responses.
  • Its input steers it. Anything in the context can change its behavior, including text you did not write, such as a web page or a file.

So what does the model know at the moment of a call? Two things. It knows what it learned in training, frozen at some cutoff date. And it knows what is in this call's context. There is no third source.

What does this reduce to?

An LLM call = one function evaluation. Context goes in, tokens come out. The call has no side effects.

An agent is a loop around the model

An agent is a program that wraps the model in a loop. The program holds state. It builds a context from that state and calls the model. It reads the response, runs any action the model asked for, and records the result. Then it decides whether to go around again.

State→ Context construction→ LLM call→ Decision: answer or action→ Tools and environment→ New state, then repeat

Here is a complete minimal agent. It is short on purpose.

def run_agent(task, tools, max_steps=30):
    messages = [system_prompt(), user(task)]
    for step in range(max_steps):
        reply = model(messages, tools)       # the only "intelligent" line
        messages.append(reply)
        if not reply.tool_calls:
            return reply.text                # the model proposes: done
        for call in reply.tool_calls:
            result = execute(call)           # your code runs it, under your rules
            messages.append(tool_result(call.id, result))
    return "stopped: step budget used up"

Look at what each line does. One line calls the model. Every other line is ordinary code you write and control. The list of messages is the state. Sending the list is context construction. The if is the stopping rule. The execute call is where the world changes.

Sophisticated agents add a lot to this skeleton. They add memory, plans, subagents, approvals, sandboxes, and checkpoints. Each of those is an extension of one of these lines. The rest of the course adds them one at a time.

Worked example: two calls, one history

Suppose a user asks how many open bugs a project has. The agent has one tool, search_issues. Here is what the runtime sends on the first call.

// call 1: what the model receives
messages: [
  {"role": "system", "content": "You are Patch, a coding agent..."},
  {"role": "user",   "content": "How many open bugs do we have?"}
]
tools: [search_issues(label: string, state: "open" | "closed")]

The model does not search anything. It replies with a request.

// the model's reply
{"role": "assistant", "tool_calls": [
  {"id": "call_1", "name": "search_issues",
   "arguments": {"label": "bug", "state": "open"}}]}

The runtime runs the search and gets 17 results. Now it calls the model again. Look at what it sends.

// call 2: what the model receives
messages: [
  {"role": "system",    "content": "You are Patch, a coding agent..."},
  {"role": "user",      "content": "How many open bugs do we have?"},
  {"role": "assistant", "tool_calls": [{"id": "call_1", "name": "search_issues", ...}]},
  {"role": "tool", "tool_call_id": "call_1", "content": "17 issues: #412, #415, ..."}
]

The model answers "There are 17 open bugs." It seemed to remember its own request. It did not. The runtime sent the whole history back, including the model's own earlier output.

Some provider APIs can store the conversation for you. You send a conversation id, and the provider rebuilds the history on its side. That moves the storage. It does not change the model. Each call still conditions on the full context assembled for that call.

Providers can also cache the computation for a repeated prefix. That makes the repeated part cheaper and faster. It does not make the context smaller. Chapter 4 covers both.

Five things people blur together

"The AI remembered my preference." "The AI ran the tests." Sentences like these hide five different parts. Name them separately and most confusion goes away.

The parts of an agent system
PartWhat it isHolds state?
Model invocationOne computation over one contextNo
Provider serviceThe API around the model. It may store conversations, cache prefixes, and filter content.Sometimes
Agent runtimeYour loop: builds context, calls the model, enforces policy, runs tools, records resultsYes, for the run
Persistent storesFiles, databases, checkpoints, memory storesYes, across runs
Per-call contextThe exact input for one call, rebuilt every timeNo, it is a view

When someone says "the agent remembers", ask which part holds the information. The answer is never the model invocation.

Systems analogy

The model is a stateless service. The runtime is your application server. The context is the request payload, assembled fresh for each request. The stores are your database.

Where it breaks: a normal service parses its request strictly and behaves the same way each time. The model reads its whole input as guidance. It can follow instructions hidden in data, and it can answer differently to the same request.

Where intelligence lives, and where agency lives

Intelligence is the part that understands and chooses. It reads the request and picks the next action. It writes the arguments, interprets the results, and writes the code or the summary. All of that happens inside model calls.

Agency is the ability to act in the world over time. That needs tools wired to real systems and permission to use them. It needs a loop that keeps going and state that persists. It also needs the authority to stop. All of that lives in the runtime.

A short version: the model proposes, the runtime disposes. The model selects actions. The runtime decides whether they happen and carries them out.

This split explains a lot. The same model behind different runtimes gives you different agents. Put it in a chat window and it is a chatbot. Give it file and shell tools and it is a coding agent. Give it a ticket queue and a refund tool and it is a support agent. A brilliant model in a runtime with no tools can only talk. A modest model in a careful runtime can be dependable within its limits.

What does this reduce to?

Intelligence = the model's choice of the next action, made inside one call.

Agency = a loop + tools + permissions + persistent state, all in your code.

Who does what

Here are the questions that trip people up most often. The answers assume a typical agent like the ones in this course, where your code runs the loop.

The model, the runtime, and the rest
QuestionAnswer
Does the model execute tools?No. It emits a structured request. The runtime decides whether to run it, then runs it.
Does the model remember previous calls?No. Each call sees only its context. The runtime, or a provider-stored conversation, supplies the history again.
Who decides to call the model again?The runtime loop. The usual rule: if the reply contains tool calls, run them and call again.
Who stores state?The runtime and its stores. Sometimes the provider stores the conversation for you.
Who executes shell commands?Runtime code, inside whatever process, container, or VM you gave it.
Who enforces permissions?Runtime code and the environment: the OS, containers, network rules, and other services. Never the model alone.
Who decides the task is finished?It is split three ways. The model proposes, the runtime stops, and some check verifies. See the next section.

"Finished" means three different things

People say "the agent decided it was done". That sentence hides three separate events, and different parts can own each one.

Propose→ Stop→ Verify
  • Propose. The model replies without tool calls, or calls a finish tool. This is a claim.
  • Stop. The runtime ends the loop. It might stop on the claim. It might stop because a step budget or a cost budget ran out. It might stop on an error rule, or because a person pressed stop.
  • Verify. Something checks the evidence. Tests pass, a file exists, an API returned success, a person accepts the result, or a separate checker agrees.

A stopped run is not a successful run. Decide your success criteria, and the evidence for them, before you build. For a coding agent, the criteria might be: the target test passes, the full suite passes, and no files outside src/ changed. Chapter 16 builds on this.

From a single call to an agent

"Agent" is not all or nothing. It helps to ask one question: who decides what happens next?

A single call

One model call does one job, such as "summarize this document". There is no loop.

A workflow

Code owns the control flow. The model fills in some steps. For example: extract fields from an invoice, validate them in code, and ask the model to fix any invalid field. You fixed the sequence in advance.

Extract→ Validate→ Fix if invalid→ Save

An agent

The model chooses the next step, inside limits the runtime enforces. "Fix the failing test" is a good example. The steps depend on what the agent finds along the way.

Choose step→ Run it→ Choose next step→ Until a stop rule

This is the course's working definition. In a workflow, code decides what happens next. In an agent, the model does, within limits you enforce.

Most real systems mix the two. A workflow can contain an agentic step. An agent can run inside deterministic guardrails. Prefer the least agentic design that solves the problem. Agents buy flexibility with cost, latency, and less predictable behavior.

Running example: Patch, version 0

Patch is the coding agent we will build up across the course. It works on a small team's web service: a Python API on PostgreSQL, deployed on AWS, with a TypeScript front end.

In version 0, Patch is not an agent at all. You paste a failing test's output and the relevant file. One model call suggests a fix. You apply it, run the tests yourself, and paste the results back. You are the loop.

suggestion = model([system_prompt(), user(test_output + file_text)])
# you: apply the fix, run the tests, paste the output back

Chapter 1 replaces you with a loop.

What goes wrong

Believing the model remembers

Why
The runtime re-sends history so smoothly that the model seems to recall it. Then a history trim or a new session breaks behavior you assumed was "learned".
Detect
Log the exact context of every call. If a fact is not in the context, the model did not use it.
Mitigate
Decide where every needed fact lives and how it reaches the context. Chapters 4 and 5 cover this.

Trusting "done"

Why
A reply with no tool calls is a claim. Models sometimes claim success they did not achieve.
Detect
Compare claims with evidence, such as test results or API responses.
Mitigate
Write success criteria into the runtime and check them before reporting success.

Putting policy in the prompt

Why
"Never delete files" written in the system prompt is a request. The model can misread it, and injected text can argue against it.
Detect
Try to talk the agent out of the rule. If wording can change the outcome, the rule is not enforced.
Mitigate
Enforce rules in runtime code and in the environment. Chapter 10 shows how.

Blaming the wrong part

Why
Everything looks like "the AI did something weird". It might be a model choice, a runtime bug, or a missing piece of context.
Detect
Traces that separate model outputs from runtime actions, with call ids.
Mitigate
Record every model call, every tool execution, and every result. Read traces before changing prompts.

You decide, AI builds

Decide yourself

  • Whether this needs an agent at all, or a workflow is enough.
  • Which actions the agent may take, and on which systems.
  • What counts as done, and what evidence proves it.
  • Where state lives, and which part holds each piece.

Delegate to AI

  • The loop code and the provider API calls.
  • Message formatting for a specific vendor.
  • Retries for network errors.
  • Logging and trace plumbing.

Check yourself

What technically makes something an agent rather than a single LLM call? (Q1)

Answer

A runtime loop in which the model chooses the next action. The runtime executes that action, feeds the result back as context, and repeats until a stop rule fires. A single call has no loop, no actions, and no feedback.

Where does agency live? (Q3)

  1. In the model's weights
  2. In the runtime: the loop, the tools, the permissions, and the state
  3. In the system prompt
Answer

In the runtime. The model selects actions. The ability to carry them out, keep going, and stop lives in your code.

What does the model know at the moment of a call? (Q4)

  1. Everything the agent has seen so far
  2. What it learned in training, plus this call's context
  3. Its training, plus everything in the provider's storage
Answer

Training plus this call's context. Stored conversations and memory only matter once something puts them into the context.

The model replies with no tool calls. Is the task done?

Answer

Not necessarily. The model proposed that it is done, and the runtime probably stops the loop. Success still needs evidence, such as passing tests.

Takeaways

  • The model is a function: context in, response out. It runs nothing and keeps nothing between calls.
  • An agent is a loop of ordinary code around that function. Only one line calls the model.
  • Intelligence lives in the model's choices. Agency lives in the runtime's loop, tools, permissions, and state.
  • "Finished" splits into propose, stop, and verify. Only evidence counts as success.
  • Prefer the least agentic design that works. A workflow is often enough.
