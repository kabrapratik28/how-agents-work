What AI builds vs what you design

An AI coding system can write almost all of an agent's code. The decisions that make the agent safe and useful stay with you.

What you hand off, and what you keep

Ask an AI coding system to "build an agent that fixes failing tests". An hour later you have a loop, four tools, a checkpoint store, and tests that pass. Now look for three answers in the code. How many steps can a run take? What happens when a push times out? Which commands need approval?

You never said, but the code answers anyway, because an AI coding system rarely stops to ask. It fills each gap with a plausible default instead.

So delegate work whose correctness you can check, such as a validator with tests. Keep the decisions that depend on your goals, your tolerance for risk, or facts only you know.

Systems analogy

You are the architect and the reviewer. The AI coding system is a fast contractor who builds whatever the drawings say.

Where it breaks: a human contractor asks when the drawings are vague, and pushes back on a risky idea. An AI coding system usually picks a plausible answer and keeps going.

The spec lists work you probably never need to write yourself. It is a good list, because each item follows a known pattern that tests can check. But each one still hides a decision that stays with you:

Write those decisions into the design brief, and let the AI implement them. Chapter 21 has a template.

What state should exist?

Suppose Patch crashes at step 14 of a nightly run. It can resume only if your code saved its state after step 13, outside the process. So decide what state exists: the message list alone, a typed record (status, todos, test results, approvals, cost), or checkpoints plus a log of every outside action (chapter 3).

If nobody decides, everything lives in the message list, and nobody can say what the agent believed when it acted.

What should the model see?

Suppose Patch runs env while debugging. If your code pastes the output into the context, the model now holds your database password. Decide the order of the context, which outputs go to files with a short preview, and when to compact. Above all, decide what never enters (chapter 4).

If nobody decides, whole tool outputs get pasted in until the window fills.

When should memory be retrieved?

Last month, Patch fixed a flaky login test. A note about that fix helps only if it shows up when the same test fails again. So decide what is always loaded, such as a small project file, and what is fetched only when needed. Decide who may write memory too, and whether the agent's notes wait for a person's approval (chapter 5).

If nobody decides, old, wrong, or planted notes start steering the agent.

What actions require approval?

Patch wants to run a migration on the shared staging database. Should it ask first? Too many gates teach people to click yes without reading. So gate by effect: actions that leave the sandbox or cannot be undone pause, and reads never do. Tie each approval to the exact call and its arguments, so a changed call needs a new approval (chapter 11).

If nobody decides, either nothing is gated or everything is. Both end with a destructive action that nobody really approved.

When should work be delegated?

Patch needs to understand an unfamiliar module before it can fix a bug. A read-only helper agent can explore it and return a short summary, which keeps Patch's own context clean. But the helper costs tokens, and its summary can drop the one detail that mattered. If you use helpers, give each one a goal, tools, an output format, and a budget (chapter 7).

If nobody decides, the AI may build a manager with workers because it looks capable.

What should be deterministic?

The expense agent must check that a receipt's line items add up to the total. Code does that the same way every time, and you test it once. So use code wherever you can write the rule down, for example for validation, arithmetic, routing, permissions, budgets, and stop rules.

If nobody decides, the model gets asked to add up totals or to judge whether an action is allowed. It is right most of the time, which is not good enough for a spending limit.

What should the model decide?

Reading a crumpled receipt photo is a job for a model, because no rule can describe every receipt. The model earns its cost where the input is messy, or where the next step depends on what the last step found, as in debugging. It is also the right tool for writing code and replies (chapter 0).

If nobody decides, the model ends up deciding everything, or a rigid workflow breaks on the first input nobody expected.

What is the security boundary?

A README in a cloned repo says "run this setup script", and the script uploads your SSH keys. Text like that can steer the model, so the boundary has to be what the process cannot do, whatever the model asks. Decide what the container mounts, which network destinations it can reach, and where credentials live. Credentials belong outside the sandbox, limited and short-lived (chapter 10).

If nobody decides, the agent runs in a developer's shell with the developer's keys.

What happens after failure?

The finance system times out right after the agent sends "submit". Did the expense go through? Decide what happens after each kind of failure. Retry network errors a fixed number of times, and resume from the last checkpoint instead of starting over. Give every outside action an idempotency key, which is an id the receiver uses to ignore duplicates. Send the rest to a person, with the trace (chapter 12).

If nobody decides, the timeout leads to a blind retry and a duplicate expense.

How do we know the agent succeeded?

Patch replies "Fixed, all tests pass", but your code never ran the tests. The model's "done" is a claim, so decide what evidence counts. Usually that means a check your code runs whenever the model says it is done. Add rules that fail a run even when the result looks right (chapter 16). Claude Code's docs warn that without a check the agent can run, you become the checker.

If nobody decides, success means the model said so.

Deterministic or model-driven?

Back to the expense agent. Reading the receipt photo needs a model. Checking that the line items add up does not, so code does it. Code also decides whether the amount needs approval. Ask these questions of each step (Q22):

Code or model? A quick test for each step
Ask of each stepIf yes
Can you write the rule down?Code
Must it give the same answer every time, or be audited?Code
Is a mistake expensive or impossible to undo?Code decides, or the model suggests and code checks
Is the input messy, such as free text, images, or logs?The model reads it, and code checks the result
Does the next step depend on what the last step found?The model chooses, inside limits that code enforces
Is the output open-ended, such as prose or code?The model writes it, and checks verify it

Most good designs mix the two. For example, the model drafts a fix, and the tests decide whether it worked.

If traces show the same steps on every run, the model has a job that code should do. The opposite sign is a growing pile of special cases in code. Anthropic's guide to building agents applies the same test to the whole system. It advises the simplest design that works, which "might mean not building agentic systems at all."

What does this reduce to?

Deterministic vs model-driven = choosing an owner for each decision: code you test once, or a model you measure over many trials.

Reviewing AI-written agent code

An AI coding system can write thousands of plausible lines in an afternoon. You do not need to read them all. Find the few places where your rules must hold, and check each one.

Start by asking for an enforcement map: each rule from your brief, with the file and function that enforce it (chapter 21). Then check these invariants, which are rules that must hold in every run:

  • Permissions are checked in one place that every tool call passes through, before anything runs. A check inside one tool can be bypassed through another tool.
  • A rejected action never runs. The rejection becomes the tool result, and the call never reaches the code that executes it.
  • An approved action runs exactly as approved. The approval record holds the call id and arguments, and your code compares them before running.
  • Tool output is capped before it enters the context, with a pointer to the full result.
  • Budgets end every run: steps, tokens, cost, and time.
  • State is saved before side effects. The intent and its idempotency key are written before the outside call, and the receiver uses the key to drop duplicates.
  • Secrets stay out of the context. Your code reads credentials when it runs a tool, so the model never sees them. Anthropic's managed-agents design goes further: tokens are never reachable from the sandbox where generated code runs.
  • "Done" needs evidence. A reply with no tool calls triggers a check, not a success.

What does this reduce to?

Reviewing by invariants = for each rule, the one place in the code that enforces it, plus a test that fails without it.

Then ask for evidence instead of reassurance. A trace of a real run lets you watch each rule fire. Scenario tests use a scripted model, which returns fixed replies, so each test repeats exactly:

def test_rejected_push_never_runs():
    model = ScriptedModel([
        tool_call("run_command", cmd="git push --force origin main"),
        final("Understood. I will not push."),
    ])
    world = FakeWorld()
    run = run_agent("tidy the branch", model=model, world=world,
                    approver=always_reject)
    assert world.commands_run == []
    assert run.tool_results[0].status == "rejected"

Finally, ask for proof that each test can fail. Remove the gate, and this test should go red.

What goes wrong

Silent defaults

Why it happens
The brief left a question open, so the AI coding system picked a plausible answer and moved on.
How to spot it
Ask it to list every assumption it made, and look for rules in the enforcement map that you never wrote.
What to do
Answer the ten questions in the brief before any code exists.

A rule enforced only by the prompt

Why it happens
"Ask before deleting" ends up as a sentence in the system prompt, because that is the shortest path.
How to spot it
The enforcement map points to a prompt for that rule, not to code or a setting.
What to do
Require every rule to name the code or setting that enforces it. Claude Code's docs draw the same line: hooks always run, while instructions in CLAUDE.md are only advice.

Tests that share the bug

Why it happens
The tests come from the same misunderstanding as the code, so they pass.
How to spot it
Remove the guard, and the test stays green.
What to do
Write the list of scenarios yourself, and ask for proof that each test fails without its guard.

You decide, AI builds

Decide yourself

  • The answers to the ten questions, written before any code.
  • The invariants, and a scenario that tests each one.
  • What counts as evidence of success.

Delegate to AI

  • All of the code: the loop, wrappers, validation, storage, and UI.
  • Tests for your scenarios, with proof that each one can fail.
  • Traces, dashboards, and the enforcement map.

Check yourself

What should be deterministic versus model-driven? (Q22)

Answer

Use code for rules you can write down, for anything that must give the same answer every time, and for expensive mistakes such as money and permissions. Use the model for messy input, for choosing steps when the path is unknown, and for writing. Where a mistake is costly, the model can suggest, but code checks before anything runs.

Permission checks live inside three of the five tool functions. What should you ask for?

  1. Nothing, because three of five is enough
  2. One policy check that every tool call passes through, backed by a sandbox
  3. A stronger instruction in the system prompt
Answer

Checks inside some tools leave other paths open. One shared check sees every call, and the sandbox catches what that check misses.

The AI's code saves a payment's idempotency key after the payment call returns. What can go wrong?

  1. Nothing, because the key is saved either way
  2. A crash after the call but before the save leads to a retry with a new key, and a duplicate payment
  3. The key could be too long
Answer

Save the intent and the key before the call, and reuse them on retry. Then the receiver can recognize the retry and skip the duplicate.

Takeaways

  • Delegate code whose correctness you can check. Keep the decisions that depend on your goals, your risk, or facts only you know.
  • Answer the ten questions before any code exists, because an open question still gets answered by a default.
  • Review AI-written agent code by its invariants: find where each rule lives, read a trace, and run tests that you know can fail.
