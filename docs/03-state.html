Chapter 3 · The core loop

State

An agent's state lives in your runtime and in the world around it. The model sees only a view of that state, rebuilt for every call.

Five kinds of state

Ask "where is the agent's state?" and you can get five different answers. They differ in who holds them, how long they last, and whether the model sees them. Most design mistakes in this area come from mixing two of them up.

Conversation

The conversation is the message log. It holds user messages, the model's replies and tool calls, and tool results. Each entry has a role, and each tool result points back to its call id. It usually only grows: new entries go on the end.

messages = [
    {"role": "user", "content": "The auth test fails. Fix it."},
    {"role": "assistant", "tool_calls": [
        {"id": "call_1", "name": "run_command",
         "arguments": {"cmd": "pytest tests/test_auth.py"}}]},
    {"role": "tool", "tool_call_id": "call_1",
     "content": "FAILED test_login_expired_token ... 1 failed, 11 passed"},
]

The conversation is not the context. It is the main source the runtime draws on to build the context. Early in a run the two look identical, because the runtime sends everything. They drift apart once the log outgrows the window, or once the runtime starts choosing.

Usually your runtime keeps the list. Some provider APIs can store it for you, as chapter 0 showed. That moves the storage. It does not change the idea.

Context: a view, rebuilt every call

The context is exactly what one model call receives. It is not stored anywhere as the truth. The runtime builds it from state, sends it, and lets it go.

def build_context(state, budget):
    parts = [system_prompt(), tool_definitions()]
    parts += render_task(state)                  # status, plan, last test result
    parts += recent_messages(state["messages"], budget)
    return parts                                 # a projection, not a copy

Think of it as a query over state. The same state can produce different contexts, depending on the budget and on what the runtime decides is relevant. A summary can stand in for old messages. A large file can appear as a short preview plus a path.

Hold one rule for now. If something is not in the context, the model cannot use it on this call. Chapter 4 is about choosing what goes into the view.

What does this reduce to?

Context = render(state, budget), computed fresh for each model call.

How real systems do it

Three systems shrink the view without deleting the log.

  • Deep Agents (0.7.28): summarization records a cutoff and a summary. The model sees the summary plus recent messages, while state keeps every raw message.
  • Pi (1.3.0): a compaction summary is a new entry in the session file. The original entries stay.
  • Hermes (v0.22.2): compaction marks old message rows as compacted instead of deleting them. They stay searchable.

Runtime state

Runtime state is what the loop itself tracks. These are the variables your code needs to run the task. Here is a coding agent's state halfway through a run.

state = {
    "messages": [...],
    "status": "running",        # running | waiting_for_approval | done | failed
    "step": 7, "max_steps": 30,
    "cost_usd": 0.42, "max_cost_usd": 2.00,
    "todo": [{"task": "fix the expiry check", "status": "in_progress"}],
    "pending_approval": None,
    "files_read": ["auth/session.py"],
    "files_changed": ["auth/session.py"],
    "last_edit_step": 5,
    "last_test": {"cmd": "pytest tests/test_auth.py", "exit": 0, "after_step": 6},
}

The fields do different jobs. Some steer the loop: status, step, budgets, and pending approvals. Some record evidence: the files changed and the last test run. Some exist for the model: the todo list gets rendered into each context.

The model never writes this object directly. It asks for tool calls. The runtime runs them and updates state from the results, not from what the model claims.

Systems analogy

Agent state is application state. The runtime is the server, the state object is its store, and the context is a page rendered from that store for one request. Tool results are events that update the store.

Where it breaks: a rendered page goes to a person, and code enforces every rule. Here the page goes to a model that picks the next action from it. Leave a fact out of the view and the decision changes. Put a stale fact in and the model acts on it. And the model cannot write to the store. Its tool calls are requests that your runtime applies or refuses.

External world state

World state is everything the agent acts on: files, databases, tickets, and deployed services. It exists without the agent. Other people and processes change it too.

The agent never holds the world. It holds observations of it, and every observation has a time, stated or not. The file it read at step 3 is a snapshot. By step 9, a teammate may have pushed a change, or a formatter may have rewritten the file.

Tools are the only window. A read tool copies part of the world into the conversation. A write tool changes the world and returns a report. The report is a claim about the world, not the world itself. A later read can confirm it.

Persistent state

Persistent state is whatever survives the process. Ask a blunt question: if the runtime crashes now, what can you get back?

  • Session logs. The conversation, saved as it grows, so a person can pick it up later.
  • Checkpoints. A snapshot of runtime state after each step, so the run can continue where it stopped.
  • Artifacts. Saved tool outputs, reports, and patches.
  • Memory stores. Facts curated for future runs.

Order matters around side effects. Record the intent before an action, and the outcome after it. A crash between the two then leaves an "outcome unknown" record you can check, instead of no record at all. Chapter 12 covers checkpoints and the harder problem of actions that must not repeat.

Which copy is true?

The same fact often lives in several places. The file is on disk. A copy sits in the conversation from an earlier read. A summary mentions it. The runtime's files_changed list names it. When the copies disagree, you need a rule for which one wins.

A good default: the world is the truth for world facts, and runtime state is the truth for facts about the run. Everything in the context is a cached view of one of those.

Three habits follow from that rule.

  • Re-read before you write. Edit tools take the old text and fail if it changed.
  • Expire derived facts. A passing test result goes stale the moment a file changes, so record which step produced it.
  • Prefer references to copies. Keep a path and a line range in state, not a pasted file.
def tests_still_pass(state):
    t = state["last_test"]
    last_edit = state["last_edit_step"] or 0
    return t is not None and t["exit"] == 0 and t["after_step"] > last_edit

That check refuses "done" when the last edit came after the last passing run.

Events and reducers

One dependable way to keep state straight is to record events, not just current values. Each step appends events: a call was requested, a call was denied, a file changed, the tests ran. Current state is a fold over those events. Front-end developers know this as the reducer pattern. On the server it is called event sourcing.

def apply(state, event):                   # old state + one event -> new state
    if event.type == "file_edited":
        if event.path not in state["files_changed"]:
            state["files_changed"].append(event.path)
        state["last_edit_step"] = event.step
    elif event.type == "tests_ran":
        state["last_test"] = {"cmd": event.cmd, "exit": event.exit_code,
                              "after_step": event.step}
    elif event.type == "approval_decided":
        state["approvals"].append((event.call_id, event.decision))
    return state

state = reduce(apply, events, initial_state())   # replay to rebuild

The log pays for itself. Replaying it rebuilds state after a crash. Reading it tells you what happened and in which order. Stepping through it is how you debug a bad run.

How real systems do it

  • Pi (1.3.0): a session is an append-only JSONL file whose entries form a tree. The system prompt and tool list are entries too, so replaying a branch reproduces exactly what the model saw.

Notice the pattern. The model sees what changes its next decision. The runtime keeps what it needs to control the loop, enforce rules, and verify results.

What the model sees, and what it does not

Every field in state needs a decision. Show it, summarize it, reference it, or keep it out.

  • Show what changes the next decision: the request, recent results, the plan, and the files changed.
  • Summarize what is long but still relevant, such as old turns and big test logs.
  • Reference what is big and only sometimes needed: full outputs, whole files, earlier sessions. A path costs a few tokens, and a tool can fetch the rest.
  • Keep out what the runtime enforces or the model must not have: approval mechanics, credentials, and other users' data.

Credentials are the firm rule. A secret in the context can end up in a log, a commit message, or a reply. Keep secrets inside the tools that use them, outside the model's view. Chapter 10 covers why.

Budgets are a judgment call. Showing "step 27 of 30" can help the model wrap up. It can also make it rush. Either way, the runtime enforces the limit.

How real systems do it

  • Pi (1.3.0): a tool result has two parts. content goes to the model. details serves the interface and state, and is never sent.
  • Hermes (v0.22.2) re-injects the todo list after every compaction, and caps it at 256 entries for that reason. It also removed its "context pressure" warnings, because they made models give up early on complex tasks.
  • Deep Agents (0.7.28) keeps background task ids in their own state field, so compacting the history cannot lose them.

State vs memory

State and memory both keep information outside the model. They differ in purpose and lifetime.

  • State serves the current run. Where are we, what have we done, what is pending?
  • Memory serves future runs. What should we know next time?
  • State is created with the run and finished with it, though you may keep it for audit. Memory is written on purpose, curated, and read back later.

They overlap. A saved session is persistent state. If a later run searches it for a similar bug, it is acting as memory. Chapter 5 takes this further.

What does this reduce to?

State = what the run needs now. Memory = what you chose to keep for later, plus a way to find it again.

Running example: Patch gets a state object

Patch version 3 keeps a state object next to its message list. The runtime updates it from tool results, not from what the model says. The done check now reads evidence from state: the last test run passed, and it ran after the last edit.

# Patch v2: the message list was the only state
- messages = [...]
# Patch v3: a state object the runtime owns
+ state = {
+     "messages": [...],
+     "status": "running",          # running | waiting_for_approval | done | failed
+     "step": 0, "max_steps": 30,
+     "files_read": [], "files_changed": [],
+     "last_edit_step": None,
+     "last_test": None,            # {"cmd", "exit", "after_step"}
+     "approvals": [],
+ }

Patch still sends the whole message list on every call. As runs get longer, that stops fitting. Chapter 4 gives Patch a context builder.

What goes wrong

Acting on a stale view

Why
The model edits a file based on a read from many steps ago. Someone changed the file since.
Detect
Edit preconditions fail. Diffs touch lines the model never saw.
Mitigate
Compare-and-swap edits. Re-read before writing. Record when each observation was made.

State that lives only in the context

Why
The plan exists only as old messages. Compaction or trimming removes them, and the agent loses the plan.
Detect
Behavior changes right after a compaction.
Mitigate
Keep task state in runtime state, and render it into each context.

Stale evidence

Why
"Tests passed" was true at step 6. The model edited again at step 8.
Detect
The done check passes, but CI fails.
Mitigate
Tie each piece of evidence to the step that produced it. Expire it on every change.

Showing the model everything

Why
The runtime dumps the whole state object into the prompt: internal flags, raw logs, every field.
Detect
The context grows with fields the model never uses.
Mitigate
Render a short view for the model. Keep control fields in code.

Lost on a crash

Why
Run state lives only in process memory.
Detect
Kill the process mid-run and try to resume.
Mitigate
Save the log and a checkpoint after every step.

Check yourself

What is state in an agent, and who holds it? (Q6)

Answer

Everything the system tracks across steps: the conversation, runtime variables such as step counts, plans, and approvals, the world the agent acts on, and whatever it saves to resume. The runtime and its stores hold it, and the world holds itself. The model holds none of it.

How are state and memory different? (Q8)

Answer

State serves the current run and ends with it. Memory is information chosen and curated for future runs, with a way to retrieve it. They overlap: a saved session is state, and it acts as memory when a later run searches it.

The model's final message says "all tests pass". What should the runtime check before it agrees?

  1. Nothing. The message is clear.
  2. The last test result in state, and whether that run came after the last edit
  3. A summary of the conversation
Answer

The message is a claim. The evidence is the recorded test run, and it only counts if no edit came after it.

What does the model know at a given moment, and what is context? (Q4, Q5)

Answer

Its training, plus the context of this call. The context is a view of state that the runtime built for this one call. Anything else the agent holds must be put into that view, or fetched with a tool.

Takeaways

  • There are five kinds of state: conversation, context, runtime state, world state, and persistent state.
  • Context is a view of state, rebuilt for every call. It is never the source of truth.
  • The runtime owns state. The model changes it only through tool calls the runtime applies.
  • The world is the truth for world facts. Re-read before writing, and expire evidence when things change.
  • Show the model what changes its next decision. Keep control, enforcement, and secrets in code.
  • State serves this run. Memory is what you keep for later runs.
