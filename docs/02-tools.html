Tools

Tools let a model change things in the world, but the model never touches them. It writes a request, and your code decides whether to run it.

What a tool really is

Patch has a tool for searching code. The spec describes it like this:

name: search_files
input:
    query: string
output:
    matching files

The model sees only a short entry like this: a name, a sentence about what the tool does, and the arguments with their types. Your code holds the rest. That is the function that searches the files, plus rules such as "read-only, and only inside the repository".

The model picks tools from the visible part alone. So a tool's description works like a prompt, and a vague description leads to wrong calls.

What does this reduce to?

Tool use = structured model output + runtime function dispatch. The output names a function and its arguments, and your code looks the function up by name.

The life of one call

Say the model wants to find where Patch checks token expiry. It replies with a request instead of text:

// the model's reply
{"role": "assistant", "tool_calls": [
  {"id": "call_1", "name": "search_files",
   "arguments": {"query": "expires_at"}}]}

// what your runtime adds to the conversation after running it
{"role": "tool", "tool_call_id": "call_1",
 "content": "auth/session.py:5: return token.expires_at >= now - ..."}

Your runtime (the code that runs the agent loop) checks the request and runs the search. Then it adds the output to the conversation with the same id. The id is how a result finds its request, which matters when the model asks for several calls at once.

The model is not waiting while the tool runs, because its call has already ended. Your runtime calls it again later, with the result in the history. Vendors name these fields differently, but the flow is the same everywhere:

Systems analogy

A tool call works like an RPC request. The tool list is the interface definition, and the call id matches each reply to its request. Your runtime acts as the server: it checks the request, runs it, and replies.

Where it breaks: the caller is a model, not compiled code. Nothing type-checks its request, so it can pick the wrong tool or follow instructions it read in a file. It also does not wait for the reply. It stops, and your code starts it again with the reply in its input. So treat every request as untrusted input.

Schemas: the contract for arguments

Patch sends this definition of search_files with every call:

{"name": "search_files",
 "description": "Search for literal text in files under the workspace. ...",
 "parameters": {
   "type": "object",
   "properties": {
     "query": {"type": "string", "description": "Text to find, not a regex"},
     "path": {"type": "string", "description": "File or folder. Default: all"},
     "max_results": {"type": "integer", "minimum": 1, "maximum": 50}},
   "required": ["query"],
   "additionalProperties": false}}

The parameters part is a JSON Schema, a standard format for describing JSON data. Here it says that query is a required string. Frameworks usually generate the schema from your function's types, so you rarely write one by hand.

A few schema choices prevent mistakes. A fixed list of allowed values, such as "open" or "closed", stops the model from inventing a third. Rejecting unknown fields helps too, because a field your code silently ignores is a hidden bug.

But a schema checks only the form of an argument. It cannot tell that ../deploy/prod.env points outside the repository.

Validating arguments

Each request in this table fails a different check:

Four checks before a tool runs
CheckQuestionA request that fails it
ParseIs it complete, valid JSON?The reply was cut off in the middle of the arguments
SchemaRight fields and types?max_results: "all" where a number is required
Current stateDoes it still make sense?An edit whose old text is no longer in the file
PolicyIs it allowed?Reading ../deploy/prod.env, outside the workspace

Treat arguments like a request body from the internet, because they are input you did not write. A library can do the first two checks. The last two need your own rules about what exists now and what is allowed. When a check fails, your runtime skips the tool and returns an error result with the same call id. The model reads it and can try again.

The third row is a stale object. The model read a file at step 3 and asks to edit it at step 9, but someone changed the file in between. A good edit tool takes the old text and refuses if it no longer matches, like a compare-and-swap. So a stale edit fails loudly instead of overwriting a teammate's change (chapter 3).

When a call fails

Suppose the model asks for auth/tokens.py, but the file is called auth/token_utils.py. Your runtime returns this result: "No such file: auth/tokens.py. Similar: auth/token_utils.py." On its next call, the model asks for the right file.

So return errors to the model as tool results, instead of crashing the run or hiding the failure. Say what went wrong and what to try next, because the model can only fix what it can see.

Who handles which failure
FailureWho handles it
Network timeout, rate limitYour runtime retries after a short wait, then longer ones (backoff). The model sees the error only if the retries run out.
Wrong arguments, denied by policyThe model, from an error result that says what to change
Missing file, stale objectThe model, from an error result with a hint
A bug in the toolThe model gets an error result, and you get an alert
The same failure again and againYour runtime stops the run or asks a person

A failing test is not a tool error. If pytest runs and two tests fail, the tool did its job, and the failures are what the model asked for.

Every call needs exactly one result before the next model call, and some APIs reject a history with gaps. So after a crash or a cancel, your runtime still records a result, such as "cancelled".

Big outputs

Patch runs pytest -v, and pytest prints 1,227 lines. Your runtime saves the full output to a file and returns a short preview instead:

exit code 1
============================= test session starts =============================
collected 1200 items
[... 1,220 lines truncated. Full output saved to .patch/outputs/call_1.log ...]
FAILED tests/test_auth.py::test_login_expired_token - assert 200 == 401
FAILED tests/test_billing.py::test_refund_rounding - assert ...
================== 2 failed, 1198 passed in 48.31s ==================

The preview keeps the first and last lines. The first lines show what ran, and the last lines usually hold the summary. The marker in the middle says how much was cut and where the rest is, so the model knows the preview is incomplete.

Structured output needs more care, because cutting JSON at a character limit leaves invalid JSON. Drop whole items instead, and say how many you dropped. Chapter 4 covers what to do when the context fills up anyway.

How real systems do it

  • Pi (1.3.0) cuts read and bash output at 2,000 lines or 50 KB. Bash saves the full output to a temp file and tells the model where it is.
  • Deep Agents (0.7.28) writes tool results over 20,000 tokens to a file named after the call id. The model sees the first 5 and last 5 lines, plus the path.

Several calls at once

The model asks to read auth/tokens.py and auth/session.py in one reply. Your runtime starts both reads. The second finishes first, and then the first fails because the file does not exist.

So your runtime matches each result to its request by call id, not by the order they finish. It returns every result, including the error, so one failure does not erase the other result.

Only independent calls can run together. Finding a file and reading it takes two steps, because the read needs the search result. Two writes to the same file at once are a race, so your runtime should refuse them even if the model asks.

Structured outputs

Patch can end a run by calling a tool instead of writing a final message:

submit_result(
    summary="Removed the 10-minute grace period in auth/session.py",
    files_changed=["auth/session.py"],
    tests_passed=True,           # a claim, not evidence
)

Your runtime offers submit_result with a schema for the final answer. So the run ends with data your code can read, not prose it has to parse. That is structured output: the model fills in a fixed shape instead of writing free text.

Some providers offer constrained decoding: they restrict what the model can generate, so the output always matches the schema. Without it, your runtime checks the output and asks for a retry when it is wrong. Either way, the content can still be false. The model filled in tests_passed too, so your runtime should check the last test run itself.

How the model finds tools

Patch has four tools, so its runtime sends all four definitions with every call. An assistant with 300 tools cannot, because each definition costs tokens on every call, and similar tools make choices harder.

There are four common fixes. A static list sends the same tools every time. A filtered list hides tools that cannot work right now, such as one with missing credentials. A tool server lists its tools on request. Tool search gives the model one search tool over a large catalog, and the runtime loads only the definitions it asks for.

MCP (Model Context Protocol) is a standard for tool servers. An MCP server tells your runtime which tools it has, and it runs the calls your runtime forwards. MCP is not an agent loop, because your runtime still decides what runs. It is not a security boundary either. The server's tools have whatever access the server has, and their text in your context is untrusted.

What does this reduce to?

An MCP tool = a tool whose definition and code live in another process, reached through a standard protocol.

Effect classes and destructive tools

run_command("pytest") only reads files, but run_command("rm -rf build") deletes them. Both use the same tool, so the tool name says nothing about the risk.

So sort each tool, or each call, by what it can change. This course calls that its effect class:

Three effect classes
ClassExamplesTypical treatment
Read-onlysearch_files, read_fileRuns freely, within its scope
Reversible writeedit_file in a git repoRuns, because git can undo it
External or irreversibleSend an email, push to main, DROP TABLE, payNeeds approval, or gets no tool at all

Read-only does not mean harmless, because reading a secret and sending it somewhere is a leak (chapter 10). Tool design can also limit damage. For example, offer archive_table(name) instead of raw SQL, take an id rather than a pattern for deletes, and offer a dry run.

Permissions

Suppose the rule is "never delete files outside the repository". Written in the system prompt, it is only a request. The model can misread it, and text injected through a web page can argue against it. Written in the code that dispatches tool calls, it runs on every call:

def dispatch(call):
    tool = TOOLS.get(call.name)
    if tool is None:
        return error(call.id, "unknown tool: " + call.name)
    problems = tool.schema.validate(call.arguments)
    if problems:
        return error(call.id, "invalid arguments: " + "; ".join(problems))
    verdict, reason = policy(tool, call.arguments)   # "allow" | "deny" | "ask"
    if verdict == "deny":
        return error(call.id, "denied by policy: " + reason)
    if verdict == "ask":
        return pause_for_approval(call)              # chapter 11
    output = tool.run(**call.arguments)
    return result(call.id, limit(output, artifact_for=call.id))

A permission check answers allow, deny, or ask a person (chapter 11). But it covers only the paths it intercepts, so if a shell tool can delete the same files, the gate has a hole. It also cannot stop a process that finds another way. That takes a sandbox (chapter 10).

How real systems do it

  • Deep Agents (0.7.28) path rules cover the built-in file tools only. They do not cover the shell tool, custom tools, or MCP tools.
  • Hermes (v0.22.2) docs call its file write guards "defense-in-depth, not a hard boundary", because the terminal runs as the same OS user and can still overwrite those paths.

Code as the action

# one model call, many tool calls, one short result
hits = tools.search_files(query="expires_at")
for path in sorted({h.path for h in hits}):
    text = tools.read_file(path=path)
    if "timedelta(minutes=10)" in text:
        print(path, "has a 10-minute grace period")

Some agents let the model write a short script like this instead of one call per step. Your runtime runs the script in a sandbox and sends back only what it prints. So one model call can do many steps, and raw file contents stay out of the context. But the model now writes programs, so the sandbox must be tight. Tool calls inside the script should pass the same checks as direct calls.

Why tools make models so much more useful

Ask a model with no tools whether Patch's auth test passes, and it can only guess from the code you pasted. Give it run_command, and it runs the test and reads the result.

Tools give the model fresh facts and a way to act. They also give it feedback, so it can try a fix, test it, and try again. The model still decides which tool to call and what the result means. Coding suits agents well because tests give fast, honest feedback (chapter 9).

Running example: Patch gets real tools

Patch version 2 gets four tools, each with an effect class. Its runtime checks every call before it runs, returns blocked calls as errors, and saves long outputs to files.

# Patch v1: one tool, no checks
- tools = [run_command]
# Patch v2: four tools, each with an effect class
+ tools = [
+     Tool("search_files", effect="read-only"),
+     Tool("read_file",    effect="read-only"),
+     Tool("edit_file",    effect="reversible write"),   # repo only; git can undo it
+     Tool("run_command",  effect="depends on the command",
+          allow=["pytest", "git status", "git diff"]),
+ ]

Patch still cannot tell you which files it changed. Chapter 3 gives it that record.

What goes wrong

Vague or overlapping tools

Why it happens
The model picks tools from their descriptions alone, so similar tools get mixed up.
How to spot it
Traces show the wrong tool, or the same argument mistake, again and again.
What to do
Say when to use each tool and when not to. Merge tools that overlap.

Errors that end the run or vanish

Why it happens
The runtime crashes on a tool error, or returns an empty string. Either way, the model never learns what went wrong.
How to spot it
Runs end in exceptions, or the model repeats the same failing call.
What to do
Return every error as a result with a hint. Retry network errors in code, and cap repeated failures.

Rules that live only in the prompt

Why it happens
"Never touch files outside the repo" is only a request, so a confused model or injected text can ignore it.
How to spot it
Ask the agent to break the rule. If clever wording gets it through, nothing enforces the rule.
What to do
Check paths and commands in the dispatcher, and run the agent in a sandbox.

You decide, AI builds

Decide yourself

  • Which tools exist, and which actions get no tool at all.
  • The effect class of each tool, and what each class requires.
  • Output limits, and where full outputs are kept.
  • Which failures code retries, and which go to the model.

Delegate to AI

  • JSON Schema generated from typed function signatures.
  • The validation and dispatch code.
  • Retries with backoff, truncation, and saved output files.
  • Tool wrappers around existing APIs.

Check yourself

How does a tool call actually work, from the model's output to its next call? (Q9)

Answer

The runtime lists the tools in the context. The model replies with a request: a tool name, arguments, and an id. The runtime checks the request, runs the function, and adds the output to the history with that id. The model reads it on its next call.

The model calls read_file with the path ../.env. The schema says the path is a string. What should happen?

  1. It runs, because the schema check passed
  2. The policy check denies it, and an error result goes back for that call id
  3. The runtime drops the call without a result
Answer

The schema only checks that the path is a string. The policy finds that the path points outside the workspace and denies it. Nothing runs, but the model still gets a result.

Two parallel calls finish in reverse order, and the first one fails. What does the model receive?

  1. Only the successful result
  2. Two results, each tied to its call id, one marked as an error
  3. An exception that ends the run
Answer

Results attach by id, not by the order they finish. The error goes back for the call that failed, and the other result is kept.

Takeaways

  • Check every call in code before it runs. A blocked call never runs, but it still gets a result.
  • Send failures and big outputs back as results the model can act on.
  • Give each tool an effect class. Enforce permissions in the dispatcher and the sandbox, not in the prompt.
