Tools

A tool is a function your runtime exposes. The model never runs it. The model writes a request, and your code decides whether and how to carry it out.

What a tool really is

From the model's side, a tool is a few lines of text in its context. From the runtime's side, it is an ordinary function plus rules about when it may run. Here is the core, in the smallest form.

name: search_files
input:
    query: string
output:
    matching files

A tool in a real runtime has six parts.

  • Name. What the model writes to call it, such as search_files.
  • Description. When and how to use the tool, in plain words.
  • Input schema. The arguments, their types, and which ones are required.
  • Implementation. The code that runs. The model never sees it.
  • Output format. What comes back, and how big it may get.
  • Policy metadata. What the call can affect, and whether it needs approval.

Only the first three reach the model. It picks tools from their names, descriptions, and schemas alone. So a description is a prompt. A vague description causes wrong calls, just as a vague instruction does.

search_files = Tool(
    name="search_files",
    description="Search for literal text in files under the workspace. "
                "Returns matching lines as path:line: text.",
    schema={"query": str, "path": str | None, "max_results": int | None},
    run=search_impl,          # ordinary code, never shown to the model
    effect="read-only",       # policy metadata, read by the runtime
    max_output_lines=200,     # output limit, enforced by the runtime
)

What does this reduce to?

Tool use = structured model output + runtime function dispatch. The model writes a request in a known format. Your code looks up the function by name and decides whether to call it.

The life of one call

Here is the whole flow. Watch who does each step.

In messages, the request and the result look like this.

// the model's output: one assistant message
{"role": "assistant", "tool_calls": [
  {"id": "call_1", "name": "search_files",
   "arguments": {"query": "authentication"}}]}

// what the runtime appends after running it
{"role": "tool", "tool_call_id": "call_1",
 "content": "auth/session.py:3: def is_valid(token, now): ..."}

Three details matter.

  • The request carries an id, and the result carries the same id. That is how a result finds its request.
  • The model is not waiting while the tool runs. Its call has ended. The runtime calls it again later, with the result in the history.
  • Field names differ between vendors. Some APIs send the arguments as a string of JSON that the runtime must parse first. The shape is the same everywhere.

Systems analogy

A tool call is an RPC request. The tool list is the interface definition, and the schema is the IDL. The call id is a request id that matches each reply to its request. Your runtime plays the server: it parses, checks, authorizes, dispatches, and replies.

Where it breaks: the caller is a model, not compiled code. Nothing type-checks its request before it arrives, unless the provider constrains generation. It can call the wrong method, invent an argument, or act on instructions it read in a file. It also does not block on the reply. It stops, and your code starts it again with the reply as input. So treat every request as untrusted, and remember that every reply becomes part of a prompt.

Schemas: the contract

A schema says which arguments exist, what type each one has, and which are required. The definition the model sees is usually JSON Schema. You rarely write it by hand. Frameworks usually generate it from types in your code.

{"name": "search_files",
 "description": "Search for literal text in files under the workspace. ...",
 "parameters": {
   "type": "object",
   "properties": {
     "query": {"type": "string", "description": "Text to find, not a regex"},
     "path": {"type": "string", "description": "File or folder. Default: all"},
     "max_results": {"type": "integer", "minimum": 1, "maximum": 50}},
   "required": ["query"],
   "additionalProperties": false}}

A few habits make schemas easier for a model to use well.

  • Use few parameters, with plain names. Write path, not p.
  • Use enums for closed choices, such as "open" | "closed".
  • State defaults in the description, so the model knows it can leave a field out.
  • Reject unknown fields instead of ignoring them. An ignored field is a silent bug.

A schema checks shape, not meaning. A string can hold a path outside the workspace. An integer can be a valid id for the wrong customer. Those need the checks in the next section.

Validating arguments

Arguments are untrusted input. Treat them like a request body from the internet. A model can produce a wrong type, a missing field, or a value that is valid but harmful.

Validation happens in layers. Each layer catches something the one before it cannot.

Four checks before a tool runs
CheckQuestionExample failure
ParseIs it well-formed?The reply was cut off in the middle of the arguments
SchemaRight fields and types?max_results: "all" where an integer is required
SemanticDoes it make sense now?An edit whose old text is no longer in the file
PolicyIs it allowed?Reading ../deploy/prod.env, outside the workspace

The first two are mechanical, and a library can do them. The last two need your rules: which objects are current, and which actions are allowed.

A failed check never runs the tool. It produces an error result instead, tied to the same call id. The model reads it and can try again.

Stale objects deserve a name. Say the model reads a file at step 3 and asks to edit it at step 9. Someone changed the file in between. A good edit tool takes the old text as an argument and refuses if it no longer matches. That is a compare-and-swap. It turns a silent overwrite into an error the model can fix. Chapter 3 returns to this.

When a call fails

Tools fail. Files go missing, commands time out, and services return errors. What matters is what the runtime does next.

The usual rule is simple. Return the error to the model as the tool result. Do not crash the run, and do not hide the failure. Models often recover well when they can see what went wrong.

Who handles which failure
FailureWho handles it
Network timeout, rate limitThe runtime retries with backoff. The model sees it only if retries run out.
Invalid argumentsThe model, from an error result that says how to fix the call
Denied by policyThe model, from an error result that says why. It changes its plan.
Not found, conflict, stale objectThe model, from an error result with a hint
A bug in the toolThe model gets an error result. You get an alert.
The same failure again and againThe runtime stops the run or asks a person

Write error messages for the model. Say what was wrong, what is allowed, and what to try next. "No such file: auth/tokens.py. Similar: auth/token_utils.py." beats "ENOENT".

A nonzero exit code is not a tool error. If pytest runs and two tests fail, the tool worked. The failing output is exactly what the model asked for.

Every call needs exactly one result before the next model call. A call with no result leaves a hole in the history, and some APIs reject it. After a crash or a cancel, write a result anyway, such as "cancelled".

Big outputs

A tool can return far more text than the context can hold. One verbose test run can print over a thousand lines. Pasting all of it causes three problems. The context fills up. Every later call costs more, because the history is re-sent. And the lines that matter get buried.

The common fix has three parts. Cap the output at a size limit. Save the full output where the agent can reach it, such as a file. Return a preview with an explicit marker that says how much was cut and where the rest is.

exit code 1
============================= test session starts =============================
collected 1200 items
[... 1,220 lines truncated. Full output saved to .patch/outputs/call_1.log ...]
FAILED tests/test_auth.py::test_login_expired_token - assert 200 == 401
FAILED tests/test_billing.py::test_refund_rounding - assert ...
================== 2 failed, 1198 passed in 48.31s ==================

Keep the head and the tail. The head shows what ran. The tail often holds the summary. The marker matters as much as the preview. Without it, the model may treat a partial output as the whole thing.

Truncating structured output can break it. Cut JSON at a character limit and the model gets invalid JSON. For structured results, drop whole items, count what you dropped, and keep the shape valid.

How real systems do it

  • Pi (1.3.0): read and bash output is cut at 2,000 lines or 50 KB. Bash saves the full output to a temp file and tells the model where it is.
  • Deep Agents (0.7.28): tool results over 20,000 tokens go to a file named after the call id. The model sees the first 5 and last 5 lines, plus the path.
  • Hermes (v0.22.2): terminal output is capped at 50,000 characters, keeping the head and the tail.

Limits only slow the growth. Chapter 4 covers what to do when the context fills up anyway.

Several calls at once

A model can ask for several calls in one reply. It might read two files at once. The runtime can run independent calls at the same time and save wall-clock time. Three rules keep this correct.

  • Match by id, not by order. Calls can finish in any order. Each result carries its call id.
  • Handle partial failure. If one call fails, return its error and still return the other results.
  • Sequence what depends. If one call needs another's output, they cannot run together. Finding a file and reading it are two steps. Two writes to the same file are a race.

Usually the model handles dependencies by asking in separate replies. The runtime still guards against races, because it cannot assume the model got it right.

How real systems do it

  • Pi (1.3.0): runs calls concurrently by default and records results in the order the model asked for them. One sequential tool makes the whole batch sequential.
  • Hermes (v0.22.2): read-only tools run concurrently. A file write joins a parallel batch only if its path does not overlap another call's path.
  • Deep Agents (0.7.28): a second write, edit, or delete on the same path in one reply is refused.

Three things from the widget carry through the rest of the course.

  • Every result names its call id, including errors and denials.
  • Schema validation and policy are separate checks. In the policy case, the schema passed.
  • The model fixes its own mistakes when the error says how. The fix is a new call with a new id.

Structured outputs

A tool call is one kind of structured output. The model emits data in a known shape instead of free text. You can use the same mechanism for the final answer.

There are two ways to get valid structure.

  • Constrained decoding. The provider restricts generation so the output always matches the schema. Type errors disappear. Wrong values of the right type do not.
  • Validate and retry. The runtime parses the output, checks it, and sends errors back. It costs extra calls, but it works with any model.

A common pattern makes the final answer a tool. The runtime offers a tool such as submit_result, whose schema is the answer format. When the model calls it, the run ends with typed data.

submit_result(
    summary="Removed the 10-minute grace period in auth/session.py",
    files_changed=["auth/session.py"],
    tests_passed=True,           # a claim, not evidence
)

Structure helps your done check, because it has fields to verify. Verify them against evidence, though. The model filled in tests_passed too. The runtime should check the last test run itself.

How the model finds tools

The model can only call tools it knows about. Discovery is how a tool's definition gets into the context. There are four common ways.

  • A static list. The runtime sends the same tools on every call. It is simple and easy to cache. It works well for a handful of tools.
  • A filtered list. The runtime shows only the tools that work right now. A missing credential or the wrong environment hides a tool.
  • Listing from a server. A protocol such as MCP lets the runtime ask another process which tools it offers. See the next section.
  • Tool search. The model gets one search tool over a large catalog. The runtime loads only the definitions the model asks for.

Why not offer everything? Every definition costs tokens on every call. Similar tools also make the choice harder. If two tools overlap, the model has to guess.

MCP: a standard plug for tools

The Model Context Protocol (MCP) is a protocol for exposing tools from another process. An MCP server lists its tools with names, descriptions, and schemas. Your runtime passes those definitions to the model. When the model calls one, your runtime forwards the call to the server and returns the result.

MCP standardizes the plumbing: discovery and invocation. It is not an agent loop. Your runtime still runs the loop, validates calls, and decides what runs. It is not a security boundary either. A server's tools run with whatever access that server has. Its descriptions and results are untrusted text that lands in your context.

What does this reduce to?

An MCP tool = a tool whose definition and code live in another process, reached over a standard protocol. Same loop, same checks, longer wire.

Effect classes and destructive tools

Tools differ in what they can break. Give every tool an effect class. The class decides how much checking a call needs.

Three effect classes
ClassExamplesTypical treatment
Read-onlysearch_files, read_fileRuns freely, within its scope
Reversible writeedit_file in a git repoRuns, with a known way back
External or irreversibleSend an email, push to main, DROP TABLE, payNeeds approval, or gets no tool at all

Read-only is not the same as harmless. Reading a secret and then sending it somewhere is a leak. Chapter 10 covers that threat.

Generic tools blur the classes. run_command("pytest") only reads. run_command("rm -rf build") destroys. A shell tool has no fixed effect class. That is why shells get allowlists, sandboxes, or approval for anything unusual.

Design tools to shrink what a bad call can damage.

  • Prefer narrow tools for risky actions. Offer archive_table(name), not raw SQL.
  • Split reads from writes. Offer get_order and refund_order, not one tool with an action field.
  • Require exact targets. Deletes take an id, not a pattern.
  • Offer a dry run that shows what would change.
  • Make writes safe to repeat, with an idempotency key. Chapter 12 explains why.

Permissions

A permission answers one question: may this call run now? The answer is allow, deny, or ask a person.

Where you enforce it matters more than how you phrase it. A sentence in the system prompt is a request. The model can misread it, and injected text can argue against it. A check in the tool dispatcher is code. It runs on every call that goes through the dispatcher.

def dispatch(call):
    tool = TOOLS.get(call.name)
    if tool is None:
        return error(call.id, "unknown tool: " + call.name)
    problems = tool.schema.validate(call.arguments)
    if problems:
        return error(call.id, "invalid arguments: " + "; ".join(problems))
    verdict, reason = policy(tool, call.arguments)   # "allow" | "deny" | "ask"
    if verdict == "deny":
        return error(call.id, "denied by policy: " + reason)
    if verdict == "ask":
        return pause_for_approval(call)              # chapter 11
    output = tool.run(**call.arguments)
    return result(call.id, limit(output, artifact_for=call.id))

Keep two limits in mind. First, a gate covers only the paths it intercepts. If the shell tool can do what a gated file tool does, the gate has a hole. Second, a permission check is not containment. It refuses or asks. It cannot stop a process that finds another way. For that you need a sandbox, covered in chapter 10. Approval gates get their own chapter, chapter 11.

How real systems do it

  • Deep Agents (0.7.28): path rules cover the built-in file tools only. They do not cover the shell tool, custom tools, or MCP tools.
  • Hermes (v0.22.2): its docs call the file write guards "defense-in-depth, not a hard boundary". The terminal runs as the same OS user and can still overwrite those paths.
  • Pi (1.3.0) has no built-in permission system. Its docs recommend a container, VM, or sandbox instead.

Code as the action

Some agents let the model write code instead of single calls. The model writes a short script. The script calls tools as functions, loops over results, and prints what matters. The runtime runs it in a sandbox and returns only the printed output.

# one model call, many tool calls, one short result
hits = tools.search_files(query="expires_at")
for path in sorted({h.path for h in hits}):
    text = tools.read_file(path=path)
    if "timedelta(minutes=10)" in text:
        print(path, "has a 10-minute grace period")

This packs many steps into one model call. It also keeps raw intermediate data out of the context. The cost is risk, because the model is now writing programs. Run them in a sandbox. Route the tool calls inside the script through the same dispatcher, so the same checks apply.

What does this reduce to?

Code as action = the model writes a program, the runtime runs it in a sandbox, and tool calls become function calls inside it.

Why tools make models so much more useful

Without tools, a model can only answer from its training and from what you paste in. Tools add four things.

  • Fresh facts. The model can look things up now instead of recalling a snapshot.
  • Action. It can change files, run programs, and call services.
  • Feedback. It can check its own work: run the tests, read the error, try again. This turns guesses into checked results.
  • Exact work. Code computes, sorts, and counts exactly. A model doing arithmetic in its head can slip.

The model supplies judgment: which tool, which arguments, and what the result means. The tools supply contact with the real world. Each is weak without the other.

This is why coding suits agents so well. A coding agent needs only a few tools, and a test suite gives fast, honest feedback. Chapter 9 builds on this.

Running example: Patch gets real tools

Patch version 2 gets four tools. Each has an effect class. The dispatcher checks every call before it runs. Invalid and denied calls come back as error results, so Patch can correct itself. Long outputs go to files, with a short marked preview.

# Patch v1: one tool, no checks
- tools = [run_command]
# Patch v2: four tools, each with an effect class
+ tools = [
+     Tool("search_files", effect="read-only"),
+     Tool("read_file",    effect="read-only"),
+     Tool("edit_file",    effect="reversible write"),   # repo only; git can undo it
+     Tool("run_command",  effect="depends on the command",
+          allow=["pytest", "git status", "git diff"]),
+ ]
+ # every call: validate, check policy, run, cap the output

Patch still keeps no record of its work beyond the message list. It cannot tell you which files it changed or whether the last test run passed. Chapter 3 gives it state.

What goes wrong

Vague tool descriptions

Why
The description is the model's only manual. Two tools with fuzzy descriptions get mixed up.
Detect
Traces show the wrong tool, or the same argument mistake, again and again.
Mitigate
Write descriptions like docs for a new colleague. Say when to use the tool and when not to. Test them on real tasks.

Too many tools

Why
Each definition costs tokens on every call. Overlapping tools invite wrong picks.
Detect
Tool definitions take a large share of each request. Wrong-tool calls rise as you add tools.
Mitigate
Fewer, clearer tools. Load rarely used ones on demand, for example through tool search.

Swallowed or fatal errors

Why
The runtime crashes on a tool error, or returns an empty string. Either way the model cannot recover.
Detect
Runs that end in exceptions. The same failing call repeated with no change.
Mitigate
Return every error as a result with a hint. Retry transient errors in code. Cap repeats.

Output floods the context

Why
One command prints megabytes, and all of it lands in the history.
Detect
A token spike right after one tool result.
Mitigate
Cap outputs, save the full text, and return a marked preview with a reference.

Policy only in the prompt

Why
"Never touch files outside the repo" is a request. A confused model or an injected instruction can ignore it.
Detect
Ask the agent to break the rule. If wording changes the outcome, nothing enforces the rule.
Mitigate
Check paths and commands in the dispatcher. Contain the process with a sandbox.

You decide, AI builds

Decide yourself

  • Which tools exist, and which actions get no tool at all.
  • The effect class of each tool, and what each class requires.
  • Which checks run before a call executes.
  • Output limits, and where full outputs are kept.
  • Which failures code retries, and which go to the model.

Delegate to AI

  • JSON Schema generated from typed function signatures.
  • The validation and dispatch code.
  • Retries with backoff for transient errors.
  • Truncation, artifact files, and marker text.
  • Tool wrappers around existing APIs.

Check yourself

How does a tool call actually work, from the model's output to its next call? (Q9)

Answer

The runtime lists the tools in the context. The model emits a structured request with a name, arguments, and an id. The runtime parses and validates the arguments, checks policy, and runs the function. It appends the output as a result tied to that id. On the next call the model reads the result. The model never executes anything.

The model calls read_file with the path ../.env. The schema says the path is a string. What should happen?

  1. It runs, because the schema check passed
  2. The policy check denies it, and an error result goes back for that call id
  3. The runtime drops the call without a result
Answer

A schema checks shape, not meaning. The policy resolves the path, finds it outside the workspace, and denies it. Nothing runs, and the model still gets a result, so the history stays whole.

Two parallel calls finish in reverse order, and the first one fails. What does the model receive?

  1. Only the successful result
  2. Two results, each tied to its call id, one marked as an error
  3. An exception that ends the run
Answer

Results attach by id, not by arrival order. A partial failure returns the error for one call and keeps the other result.

Where should the rule "never delete files outside the repo" be enforced? (Q23)

Answer

In code on the tool path, as a check in the dispatcher, and in the environment, as a sandbox that cannot reach those files. A sentence in the prompt helps the model behave, but it enforces nothing.

Takeaways

  • A tool is a name, a description, a schema, and code. The model sees only the first three.
  • A tool call is a request. The runtime validates it, checks policy, runs it, and returns a result tied to the call id.
  • Checks come in layers: parse, schema, semantic, policy. A blocked call never runs, and it still gets a result.
  • Errors go back to the model as results. Code retries transient failures.
  • Cap large outputs with an explicit marker and a reference to the full artifact.
  • Effect classes decide how much checking a tool needs. Enforce permissions in code, not in prompts.
