Chapter 20 · Thinking like a designer

Architecture exercises

Ten design problems. Write your own architecture for each one, then compare it with one reasonable design and its tradeoffs.

How to use these exercises

These are design exercises, not programming exercises. Each one gives you a scenario and a few questions. Write your answers in the box. Your notes stay in this browser. Then open the reveal and compare.

The reveal shows one reasonable architecture. It is not the only answer. A different design can be just as good if you can defend its tradeoffs. Look for the places where you decided differently. Then ask which choice you would defend in a design review.

Every reveal covers the same ground, in the same order:

  • A diagram of the parts, labeled by who does each step.
  • The tools, each with an effect class.
  • What state persists, and where it lives.
  • What the agent remembers, if anything.
  • Whether to use subagents.
  • What triggers a run.
  • What happens when something fails.
  • Which actions need a person's approval.
  • The security boundary: what the process can touch at all.
  • What stays deterministic.
  • How to evaluate it.
  • Alternatives, and what could go wrong.

Effect classes come from chapter 2. A read-only tool changes nothing. A reversible write changes something you can undo, such as a draft or a file in a sandbox. The third class is external or irreversible: the action leaves your system or cannot be undone, such as an email, a payment, or a merged change. The tool lists below call it "External" for short. A tool whose effect depends on its arguments, such as a shell, has no fixed class.

In the diagrams, each step says who performs it. The colors repeat that. Violet is the model and blue is your code. Green is tools and the outside world. Amber is stored state, and rose is a person.

Two habits help in every scenario. First, start from the least agentic design that works (chapter 0). Let the model choose the next step only where that step depends on what the agent finds. Second, put every side effect behind code you control. The model proposes actions. Your code decides whether they run.

Some scenarios need no agent at all. Saying so, with reasons, is a strong answer. When you finish an exercise, grade your design with the rubric at the end of the page.

What does this reduce to?

A reference architecture = a diagram + tools with effect classes + a state model + rules for failure, approval, the boundary, and evaluation.

Competitor report every Monday

A product team tracks eight competitors. Every Monday by 7:00 they want a report in their team channel and a shared folder. It covers what changed last week across about 40 sources: pricing pages, release notes, product pages, job posts, and news mentions. Every claim must link to its source.

  1. What tools does it need?
  2. What state should persist?
  3. Does it need memory?
  4. Should it use subagents?
  5. Does it need scheduling?
  6. What should happen if one website fails?
  7. How should success be evaluated?
Reveal one reasonable architecture

A deterministic workflow is enough here. The sources are known in advance, and so are the schedule and the shape of the report. Code owns the control flow. The model does three jobs inside it: pull facts out of a changed page, judge which changes matter, and write the report. No step needs the model to choose what happens next.

Tools

  • fetch_page(url) Read-only Goes through a proxy with per-site rate limits. Respects robots.txt.
  • search_news(company, since) Read-only A news API with a date filter.
  • load_snapshot, save_snapshot Reversible write A versioned store of each source's text and hash.
  • post_report(week, text) External Posts once per week key. A rerun edits the same post.

Your code calls these functions. The model never sees them as tools. So text injected into a competitor's page has nothing to call.

Design decisions
DecisionThis design
Persistent statePer source: the last snapshot, its hash, fetch time, and status. Per run: the week key as run id, each source's status, extracted facts with URLs, the draft, and delivery status.
MemoryBarely any. Last week's snapshots are state, not memory. A short guide, edited by the team, says what matters and what to ignore. The ranking step always sees it. Code checks past reports so old news is not repeated.
SubagentsNo. Fetching and extracting is a parallel map in code. Each model call already sees one source, so you get isolation without delegation. Subagents would add cost and variance, with nothing to coordinate.
Triggers and schedulingYes, a schedule: Monday 06:00, due by 07:00. The week key, such as 2026-W43, makes a duplicate trigger harmless.
When things failOne site fails: retry three times over 30 minutes. Then mark it stale, keep last week's snapshot, and say so in the report: "Acme pricing: not checked, HTTP 503." A failed fetch never counts as "no change". If more than a quarter of sources fail, hold the report and alert the owner.
ApprovalsA person approves each draft for the first month. After that, none. The audience is internal, and nothing irreversible happens.
Security boundaryFetched pages are untrusted input. The model steps have no tools, so injected text can at worst distort a summary. Egress goes through the proxy. The posting credential lives in the post step, never in a context.
Deterministic partsThe schedule, source list, fetching, retries, normalizing, diffing, dedupe, quote checks, posting, and the week key.
EvaluationReplay 20 past weeks that the team labeled. Measure how many important changes the report caught, and count invented ones. Code checks that each quote appears on its linked page as fetched this week. In production, track stale sources, uncited claims (target zero), and "you missed this" replies.

Alternatives

  • One agent loop with web search, told to "research our competitors". It can find new sources. But its coverage changes from week to week, and it is hard to evaluate. It works better as a monthly discovery run that proposes new sources for a person to add.
  • A change-detection email with no model at all. If the team only needs "these pages changed", that is enough. The model adds value only by judging and summarizing.
  • One subagent per competitor. Worth it only if each competitor needs deep, open-ended research across dozens of sources.

What could go wrong

  • A site redesign makes the whole page look changed. The model then reports a price change that never happened. Normalize the text, and send large diffs to a person.
  • A source fails quietly for weeks. List stale sources at the top of the report.
  • The summary states something no source says. The quote check catches it.
  • A retry posts the report twice. Check the week key before posting.

Coding agent: fix failing CI on pull requests

A monorepo gets about 400 pull requests a day. About one in five fails CI on the first try. Most failures are small: a lint error, a type error, a stale snapshot, a test broken by a renamed function. The team wants an agent that reacts when CI fails on a pull request. It should push a fix to the branch, or explain the failure in a comment.

  1. What triggers a run? What stops the agent from triggering itself forever?
  2. Which tools does it need, and what is each one's effect class?
  3. Where does it run, and which credentials does it hold?
  4. When may it push a commit, and when should it only comment?
  5. How do you stop it from "fixing" a test by weakening it?
  6. How do you know it helps?
Reveal one reasonable architecture

An event-driven agent with one small loop per failure. Code decides whether to run at all. The model decides how to fix the failure. Code decides whether the fix may be pushed. Inside, it is Patch's loop from chapter 9, with a different trigger and a stricter exit.

Tools

  • get_ci_log(job) Read-only The failing step's log. Long logs are saved as files with a preview.
  • search_files, read_file Read-only The pull request's checkout only.
  • edit_file Reversible write Inside the sandbox checkout.
  • run_check(name) Reversible write Runs in the sandbox, using the exact command CI ran for that check. There is no general shell.
  • push_commit, post_comment External Called by the gate after the loop ends. The model cannot call them.
Design decisions
DecisionThis design
Persistent statePer pull request: attempts, the head commit each attempt saw, the outcome, and a link to the trace. The key is pull request plus head commit, so a webhook delivered twice runs once.
MemoryA knowledge file per repo: how to update snapshots, which lint fixes are safe. People curate it. Past fixes indexed by error signature are a useful extra.
SubagentsNo. One failure, one narrow task, a small context.
Triggers and schedulingThe CI-failed webhook. The agent's own commit triggers CI again. If that run fails the same way, the agent does not run again. Hard cap: two attempts per pull request.
When things failFlaky test: the rerun passes, so label it and stop. Budget used up: comment with the diagnosis so far. Branch moved during the run: discard the fix. Never force-push.
ApprovalsThe author opts in with a label. That is consent to automatic commits. Without it, the agent only comments with a suggested patch. Diffs that touch CI config, lockfiles, or test assertions always drop to comment-only.
Security boundaryAn ephemeral container with the checkout. No deploy or CI secrets. Egress to the package registry only. Pull request code is untrusted and may be hostile. The push token lives in the gate, scoped to this branch and short-lived. Pull requests from forks get comments only.
Deterministic partsTriage, the rerun, attempt caps, choosing the check, the gate's diff rules, pushing, and commenting.
EvaluationReplay 200 past failures with known human fixes. A trial succeeds if the check passes, the full CI run passes, and the diff touches no forbidden paths. In production, track how often authors keep the commit, reverts within a day, cost per attempt, and time to green.

Alternatives

  • Deterministic autofix first. Lint fixers and snapshot updates need no model. Run them before the agent.
  • Comment-only for everyone. Less value, much less risk. A good first month.
  • Run on request from a developer's machine instead. A person is present and there is more context, but nothing is automatic.

What could go wrong

  • The agent and CI trigger each other in a loop. Attempt caps and the same-failure rule stop it.
  • The agent deletes an assertion or adds a skip marker. The gate rejects diffs that remove assertions or add skips.
  • Hostile code in a pull request steals a token from the sandbox. There are no tokens in the sandbox to steal.
  • Comments on every failure annoy people. Comment only when there is a concrete diagnosis.

Customer support agent

An online store handles 40,000 orders a month and gets about 2,000 support messages a week. Common requests: where is my order, change the address, cancel, return, refund, product questions. Policy: refunds up to $100 within 30 days are automatic. Larger refunds need a person. The team wants the agent to resolve what it safely can, and hand the rest to people with a summary.

  1. Which parts are a workflow, and which need an agent loop?
  2. Which tools does it need? Which ones are external?
  3. Which actions need approval, and who approves?
  4. What does the model see for one conversation? What stays out?
  5. How might a customer's message trick it, and what stops that?
  6. What counts as a resolved conversation?
Reveal one reasonable architecture

A router in code, then a small agent per conversation with narrow tools. Refunds and replies are external actions. The refund policy is enforced inside the refund tool. The prompt can describe the policy, but only code can enforce it.

Tools

  • get_order, get_tracking Read-only Only the verified customer's orders. The customer id comes from the session, never from the model's arguments.
  • search_help(query) Read-only Policy and help articles.
  • update_address(order, address) Reversible write Only before the order ships.
  • issue_refund(order, amount, reason) External Checks the policy itself. Up to $100 within 30 days runs at once. Anything else becomes an approval request. Money goes only to the original payment method.
  • send_reply(text) External Every outgoing message passes through it, so it is logged and rate-limited.
  • handoff(summary) Reversible write Moves the conversation to the human queue.
Design decisions
DecisionThis design
Persistent stateIn the helpdesk, the source of truth: the verified customer, orders, intent, actions with their ids, status, and messages. The agent keeps no separate copy.
MemoryCustomer history comes from the CRM at use time. Help articles come by retrieval. Nothing a customer says becomes a stored fact. "You promised me a discount" is a claim to check, not a memory.
SubagentsNo. Conversations are short and independent. Scale comes from running many conversations, not many agents per conversation.
Triggers and schedulingEvents: a new message, a customer reply, a carrier update. A scheduled job follows up on quiet conversations and closes stale ones.
When things failA tool error leads to an honest reply and a handoff. The agent says a refund happened only if the tool returned a refund id. Refund retries reuse the payment provider's idempotency key, or look up existing refunds first.
ApprovalsRefunds over $100 or after 30 days, goodwill credits, and anything that mentions legal action or safety. A support lead approves. They see the order, the policy rule, the exact action, and the draft reply.
Security boundaryTools are scoped to the verified customer at the API level. The model sees this conversation, this customer's orders and history, and the policy text that applies. It never sees card details or other customers' data. A jailbroken model can at most request a refund, and the tool still applies the policy.
Deterministic partsIdentity checks, order lookup, policy thresholds, refund limits, templated status answers, routing, and response-time timers.
EvaluationReplay 500 labeled past conversations against fake order and payment services. A trial passes only with the right action or handoff, no policy violation, and no claim the tools did not confirm. In production, a conversation counts as resolved only if it stays closed for 7 days. Also track handoff rate per intent, refund dollars per conversation, and sampled audits.

Alternatives

  • A pure workflow: intent detection, forms, and templates. It is cheaper and predictable, and it covers the most common requests. Many teams start here and add the agent for the long tail.
  • Draft-only: the agent drafts and a person sends every reply. Slow, but a safe first month.
  • Separate agents per department, with handoffs between them. Useful only if departments need different tools and permissions. Each handoff is a new chance to misroute.

What could go wrong

  • Social engineering: "Send the refund to this other card." The payment destination is never a model argument.
  • The agent promises a refund the policy does not allow. Retrieve the policy text, enforce it in the tool, and state only actions a tool confirmed.
  • A timeout leads to a second refund. Use idempotency keys, or look up before retrying.
  • Everything gets handed off. Watch the handoff rate per intent, and fix the worst intents first.

Personal research agent

You want an agent that answers research questions. One example: "What do recent studies say about creatine and sleep?" Another: "Compare three vector databases for 50 million documents." It searches the web and papers, reads sources, and writes a short report with citations. It runs when you ask, sometimes for 20 minutes. Over time it should learn what you already know and which sources you trust.

  1. Is this an agent or a workflow? Why?
  2. Would subagents help? For which part?
  3. What should it remember across questions? Who approves what it remembers?
  4. What happens when sources disagree, or a page tries to give it instructions?
  5. When should it stop researching?
  6. How would you evaluate a report?
Reveal one reasonable architecture

A real agent. The next search depends on what the last one found. A lead agent scopes the question. Researcher subagents explore sub-questions in parallel, each with read-only tools and its own context. The lead writes the report from their condensed notes. Research stops when every sub-question has cited notes, or when the budget runs out. Code checks the citations.

Tools

  • web_search, search_papers Read-only Researchers only. Titles, snippets, and URLs.
  • fetch(url) Read-only Researchers only. Saves the cleaned page as a file. The model gets a preview and the path.
  • write_note(path, text) Reversible write In this question's workspace only.
  • delegate(question, budget) Read-only Lead only. Starts a researcher whose tools are all read-only. Researchers cannot delegate.
  • propose_memory(fact) Reversible write Lead only. Adds to a review queue, not to memory.
Design decisions
DecisionThis design
Persistent stateA workspace per question: the plan, sub-questions with status, notes files, the source list with fetch times and content hashes, and the draft. You can reopen a question and extend it.
MemoryA short profile you control: your background, trusted and distrusted sources, preferred format. Only the lead sees it. Past reports are indexed by topic and retrieved when a new question overlaps. The agent proposes memory changes, and you accept them.
SubagentsYes, for breadth. Sub-questions are independent, and reading pages is long and noisy. Each researcher returns at most 500 words with quotes and URLs, and details stay in files. Limits: five researchers, one level deep, a step and token budget each. One author writes the report, so the argument stays coherent.
Triggers and schedulingOn demand. An optional watch mode reruns a saved question monthly and reports only what is new. That part is a scheduled workflow.
When things failA page will not load: skip it and note it. A researcher runs out of budget: it returns partial notes, marked partial. Sources disagree: the report shows both, with citations. The lead may run one extra round on conflicts, then it stops.
ApprovalsNone for reading. Memory writes need your acceptance. No tool can spend money or post anything.
Security boundaryPages are untrusted. Injected instructions can at worst distort one researcher's notes, because researchers can only read. Any request can also leak data through its URL. So researchers never see your profile. Fetch opens only URLs that came from search results or fetched pages, never URLs the model composes. The lead has no fetch tool.
Deterministic partsBudgets, dedupe of sources by URL and hash, the quote check, report formatting, and the memory review queue.
EvaluationThirty questions where you know a good answer. Code checks that each cited quote appears in its source. A rubric grades coverage of the key points. An LLM grader can help once its grades agree with yours. Track cost and time per report.

Alternatives

  • A single agent with no subagents. Cheaper and simpler, and fine for narrow questions. Start here. Add researchers when traces show the context filling up with page text.
  • A fixed pipeline: search, take the top ten results, summarize. Cheap and predictable, but shallow. Good for news digests, weak for comparisons.

What could go wrong

  • A claim cites a real source that does not say it. The quote check catches most of these.
  • Memory narrows your view, and "trusted sources" become the only sources. Keep some results from outside the list, and show what was left out.
  • A researcher's summary drops a key caveat. The notes files keep the full text, so the lead can check.
  • A private detail leaks into a search query. The lead's briefs to researchers carry the question, not your profile.
  • Cost runs away with five researchers reading long pages. Set budgets per researcher and per run, and show the spend in the report.

Sales agent

A B2B software company gets about 300 demo requests a week. Reps waste hours on poor fits. The company wants an agent that researches each lead and scores its fit against the ideal customer profile. It should write a personal first email and book a call with the right rep. It must respect email consent rules. It must never offer discounts.

  1. Which steps are fixed, and which need judgment?
  2. Which tools and data sources does it need?
  3. Which messages need a person before they go out?
  4. How do you stop it from inventing facts about a prospect?
  5. What state lives in the CRM, and what lives in the agent?
  6. Which metrics show it is working? Which would fool you?
Reveal one reasonable architecture

Mostly a workflow per lead. Code runs enrichment, rules, and booking. The model explains edge-case scores and writes the email. A small agent handles replies. Outbound email is the riskiest action, so it sits behind a gate.

Tools

  • crm_lookup(email) Read-only Dedupe and the existing-customer check.
  • enrich_company(domain) Read-only A company data API. Each field keeps its source and date.
  • save_draft(lead, text) Reversible write Stored in the CRM.
  • send_email(draft_id) External Runs only after approval. Checks consent and the suppression list in code.
  • find_slots(rep) Read-only The rep's calendar.
  • book_meeting(lead, rep, slot) External No approval needed once the prospect picks a time. Rechecks the slot first.
Design decisions
DecisionThis design
Persistent stateAll in the CRM: the lead, enrichment fields with source and date, score and reason, draft, approval, sent message ids, replies, meeting. The agent keeps no shadow copy.
MemoryThe ideal customer profile and the messaging guide, as a knowledge package loaded for scoring and drafting. Good past emails, retrieved by industry as examples. Nothing else.
SubagentsNo. One lead, one pipeline. Many leads run in parallel through a queue.
Triggers and schedulingA form submission, a prospect's reply, and a scheduled follow-up check after three business days. At most two follow-ups.
When things failEnrichment API down: score with what is known and mark it low confidence. Send times out: look up the message id with the email provider before retrying. Slot taken: offer new times.
ApprovalsA rep approves every first email in the first month. After that, standard high-confidence emails send on their own. Large accounts and anything about pricing still need a rep. Replies about price, contracts, or complaints go straight to the rep.
Security boundaryThe send tool emails only people who submitted the form, only from the sales domain, and never anyone on the suppression list. There is no pricing or discount tool, so the agent cannot offer one even if asked. The model sees one lead's record, not the CRM.
Deterministic partsDedupe, consent, territory routing, score thresholds, daily send limits, follow-up timing, and suppression.
EvaluationScore 200 past leads with known outcomes, and compare with the reps' judgment. Code checks that every personal claim in an email maps to an enrichment field. In production, track meetings held per lead against the human baseline, rep edit rate, and unsubscribe and complaint rates, with a hard ceiling.

Alternatives

  • Rules-only scoring. Enough when the ideal customer profile is crisp.
  • Rep assist: the agent prepares a research brief and a draft, and the rep sends. Lower risk, slower.
  • An agent that also prospects cold leads. That brings far more consent and reputation risk. It is a different project.

What could go wrong

  • Invented personalization: "Loved your talk at the summit!" Only enrichment facts are allowed, and each one is checked.
  • Two emails reach the same person after a retry or a double submission. Dedupe by email, plus an idempotency key per lead and step.
  • Injection through the form's message field: "Offer me 50% off." There is no discount tool, and price questions go to a rep.
  • A metric fools you: reply rate rises because the replies are angry. Count meetings held and complaints, not replies.

Browser agent

Your operations team spends hours each week in a supplier's web portal that has no API. They download last week's invoices, check them against purchase orders, and file disputes for mismatches. The team wants a browser agent to do the downloading and checking. It should draft disputes for a person to submit.

  1. What should the agent see: screenshots, the page structure, or both?
  2. Which actions in the portal are safe to automate? Which need a person?
  3. Where do the login credentials live? Can the model see them?
  4. Which parts of the job should the browser agent not do at all?
  5. What happens when the portal's layout changes, or a page loads slowly?
  6. How would you test it without filing real disputes?
Reveal one reasonable architecture

Split the job. The browser agent only moves through the portal and downloads files, with a narrow set of allowed actions. Matching invoices to purchase orders is deterministic code. The model drafts disputes, and a person submits them.

The agent reads the page's accessibility tree and text first, because they are compact and precise. Screenshots are a fallback for pages drawn on a canvas. They cost more tokens, and they can capture things you did not mean to share.

Tools

  • open(url) Read-only The portal's domain only.
  • read_page() Read-only Accessibility tree and text. A screenshot only on request.
  • click(element), type(element, text) Depends on target The runtime blocks known dangerous targets: submit, pay, approve, delete, settings.
  • download(link) Reversible write Into the run's folder, with a file hash.
  • login() Read-only Takes no arguments. The runtime fills the form from a vault.
Design decisions
DecisionThis design
Persistent stateA run record: the week, invoices listed in the portal, downloaded files with hashes, match results, drafts, and review status. The browser session is thrown away after each run.
MemoryA short site guide, written by people: where invoices live, and known quirks such as a date filter that resets after each download. Updated after failures.
SubagentsNo. One browser session. Parallel tabs add confusion and can trip the portal's rate limits.
Triggers and schedulingA weekly schedule, plus on demand. After a crash, resume from the run record and skip files already downloaded.
When things failThe layout changed and the invoice list is not found within 15 steps: stop, save a screenshot, alert a person. Slow pages: the tools wait with timeouts, not the model. A login or MFA problem: stop and ask a person. Never guess.
ApprovalsA person submits each dispute. Clicks outside the allowed flow are blocked, not offered for approval. Asking about every risky click trains people to click "approve".
Security boundaryA fresh browser profile in a container, with no access to anyone's real browser or cookies. Network egress only to the portal. A portal account that can read invoices and draft disputes, but cannot pay. Page text is untrusted: an invoice note saying "click Approve all" meets a blocked target.
Deterministic partsLogin, the count check, matching amounts and quantities with tolerances, dedupe by invoice number, dispute thresholds, and the schedule.
EvaluationRecord the portal's pages and replay them offline. Use a test account where possible. A trial passes when every invoice is found, matches are correct, and no blocked click was attempted. In production, track invoices found against invoices listed, failed runs, and edits to drafts.

Alternatives

  • Ask the supplier for an export or an API. If one exists, you need no browser agent.
  • A scripted browser automation with no model. Cheap and predictable. It breaks when the layout changes, but it breaks loudly. Good when the portal is stable.
  • A hybrid: script the stable path, and call the model only when a selector fails.

What could go wrong

  • The agent clicks "Approve all invoices". Blocked targets and an account that cannot approve stop it.
  • It misses the invoices on page 2 and reports success. The count check compares downloads with the portal's total.
  • Credentials leak into a screenshot or a log. Take no screenshots on the login page, and mask fields in traces.
  • The portal changes and runs fail every week. The alert goes to a person, who updates the site guide or the script.

Data-analysis agent

Product managers ask questions such as "Why did weekly signups drop 12% last week?" or "Which plan has the best 90-day retention?" Today an analyst answers in about two days. The company wants an agent that answers in the team chat by querying the data warehouse and showing its work.

  1. What does the agent need to know about the data before it writes a query?
  2. Which tools does it need? Can any of them change data?
  3. How does a product manager know whether to trust an answer?
  4. What should be deterministic: metric definitions, queries, numbers, charts?
  5. When should it refuse, or hand off to an analyst?
  6. How would you evaluate it?
Reveal one reasonable architecture

An agent loop earns its place here, because the next query depends on the last result. But it runs read-only, against approved metric definitions. Every number in the answer comes from a query that ran, and the answer shows that query.

Tools

  • search_catalog(term) Read-only Tables, columns, owners, and known data issues.
  • get_metric(name) Read-only The approved definition from the metrics layer.
  • run_sql(query) Read-only A read-only role on a replica. Row, time, and cost limits are checked before it runs.
  • make_chart(result_id, spec) Read-only Renders from a stored result.
  • post_answer(thread, answer) External Called once, by code, at the end.
Design decisions
DecisionThis design
Persistent statePer question: the thread, every query with its SQL, result id, row count, and data freshness, the findings so far, and the answer. Results are stored as artifacts. The model sees aggregates and a few sample rows, not full tables.
MemoryThe metrics layer and the data catalog are the memory that matters: definitions, join paths, and known quirks such as "signups before March 3 double-count SSO users". Past answers and their SQL are retrieved for similar questions. Analysts mark good ones as verified examples.
SubagentsUsually no. Data questions are sequential. One exception: a separate checker re-derives the headline number from scratch, without seeing the first answer.
Triggers and schedulingA question in chat. A weekly metrics digest would be a workflow with fixed queries, not this agent.
When things failA SQL error goes back to the model, with a retry limit. A query over the cost limit is refused, with a narrower question suggested. Late data is reported with its freshness time. An empty result means "no data", never a guess. A question that needs a metric with no approved definition gets an "exploratory" label, or goes to an analyst.
ApprovalsNone for reads within limits. Queries over the cost cap need an analyst. There are no write tools.
Security boundaryQueries run with the asking user's data permissions. The agent cannot show anyone data they could not query themselves. Personal data columns are masked. Free-text columns are untrusted input.
Deterministic partsMetric definitions, access control, cost limits, running SQL, and the numbers in the answer. Code copies them from results. The model never retypes a number.
EvaluationOne hundred questions with analyst-verified answers. Grade the number (within a tolerance), the method (right metric, right filters), and honesty (uncertainty stated, exploratory work labeled). In production, analysts spot-check one answer in ten.

Alternatives

  • One-shot text-to-SQL with no loop. Fine for lookups such as "signups last week". Weak on "why" questions.
  • Dashboards with fixed queries. Better for recurring metrics. The agent should link to them when they exist.
  • An analyst approves each answer before it posts. Slower, and much safer at first.

What could go wrong

  • A join double-counts and produces a plausible wrong number. Approved metrics, row-count sanity checks, and the independent re-derivation all help.
  • A correlation becomes a causal claim: "Signups dropped because of the pricing change." Answers must separate observed facts from hypotheses.
  • Data reaches someone who may not see it. Queries run with the asker's permissions.
  • The model mistypes a number while writing. Code inserts numbers from results.

Autonomous debugging agent

Your on-call engineers get paged about 30 times a week. Many pages repeat: a full disk, a stuck queue, a bad deploy. The team wants an agent that starts investigating the moment an alert fires. It reads logs, metrics, traces, and recent deploys. It forms hypotheses and posts findings in the incident channel. It may also apply a few known fixes.

  1. What may the agent do on its own? What needs a person?
  2. How does it keep track of hypotheses and evidence?
  3. Which tools does it need, and what is each one's effect class?
  4. How do you stop it from making an incident worse?
  5. How does a run end? What counts as "root cause found"?
  6. How would you evaluate it before it touches production?
Reveal one reasonable architecture

An event-triggered agent that is read-only by default. It investigates in a loop and keeps an explicit hypothesis board in state. Fixes come from a short list of runbook actions. Each one needs approval and gets checked automatically afterward. A cause counts as found only when it explains the symptom and when it started, and a check confirms it, such as errors dropping after a rollback.

Tools

  • query_logs, query_metrics, get_traces Read-only Results are capped. Large outputs are saved as files with a preview.
  • list_deploys(service, since) Read-only From the deploy system.
  • search_incidents(symptom) Read-only Past incidents and postmortems.
  • update_board(hypotheses) Reversible write The hypothesis board in the incident record.
  • post_update(text) External An internal channel, so low risk.
  • propose_action(action, params) External Runs only after approval, and only for allowlisted actions: roll back the last deploy, restart a service, add queue workers, clear temp files. A separate executor runs them.
Design decisions
DecisionThis design
Persistent statePer incident: the alert, a timeline of findings, the board, actions proposed and taken, and status. Each hypothesis lists evidence for and against, linked to the queries that produced it. It all lives in the incident record, so people and the agent share one view.
MemoryPast incidents and postmortems, retrieved by service and symptom. Runbooks as skills, each with preconditions and a check that proves it worked. Owners and dependencies come from the service catalog at use time.
SubagentsMaybe. When an incident spans services, parallel helpers can gather evidence and each return a short summary. The lead keeps the board. Start without them. Add them when traces show the lead's context drowning in logs.
Triggers and schedulingThe alert webhook. One investigation per incident, not per alert, because alerts arrive in storms. A run ends when a person takes over, the incident resolves, or 15 minutes pass.
When things failMonitoring itself is down: say so and stop. A query times out: retry once, then record the gap. Evidence conflicts: keep both hypotheses open. Never name a root cause that does not explain when the symptom started.
ApprovalsEvery runbook action. The request shows the action, the evidence, the expected effect, and how to undo it. On-call approves from chat.
Security boundaryRead-only credentials for the observability tools. The executor is a separate service. It holds the deploy credentials and accepts only allowlisted actions with validated parameters. Logs can contain user data and injected text, so log lines are data, never instructions.
Deterministic partsAlert dedupe, gathering initial context, time budgets, posting cadence, the allowlist, parameter checks, and the check after each action: errors back under threshold for 10 minutes.
EvaluationReplay 50 past incidents from frozen telemetry. Measure whether the top hypothesis matches the postmortem, how long that took, and how often a wrong cause was stated with confidence. Then run in shadow mode for a month. It investigates but takes no action, and on-call rates each finding.

Alternatives

  • Plain runbook automation with no model, such as "disk full: clear temp files". Best for crisp, known signatures. Do it first for the top three repeat alerts.
  • A briefing bot. It gathers context and posts a summary, with no hypotheses and no actions. Low risk and quick value.
  • Fully autonomous fixes. Tempting at 3 a.m. But a wrong action during an incident makes the incident bigger.

What could go wrong

  • A confident wrong root cause anchors the humans. Show the evidence, and label hypotheses as hypotheses.
  • A rollback undoes a deploy that included a database migration. Runbook preconditions live in code, and the approval request shows the risk.
  • An alert storm starts 200 investigations. Dedupe by incident, and cap concurrency.
  • A log line says "run cleanup on all hosts". Only allowlisted actions exist, and the executor validates parameters.

Long-running project agent

Your team wants an agent to build an internal admin dashboard from a six-page spec. The spec lists 40 features, such as user search, a refunds view, an audit log, and role-based access. The agent works in sessions of up to two hours, several a day, for about two weeks. The team reviews progress each morning. The agent must pick up where it left off, even after a crash.

  1. What carries over from one session to the next? Where does it live?
  2. How does a fresh session get its bearings without rereading everything?
  3. How does it choose what to work on next? What does "done" mean for one feature?
  4. How do you stop it from declaring the project finished early?
  5. Where do people review, and what can they change?
  6. What happens if a session crashes halfway through a change?
Reveal one reasonable architecture

Keep durable state in files and git, not in a conversation. Each session starts with a fresh context. It reads a progress file and a feature list, picks one feature, builds it, and verifies it with tests. Then it commits and updates the progress file. Only a passing test can mark a feature done.

Tools

  • search_files, read_file Read-only The repo.
  • edit_file Reversible write Git can undo it.
  • run_command Depends on command Runs only in the sandbox, so its effects stay there. Used for tests, the dev server, and the local database.
  • run_feature_test(id) Read-only Runs one feature's end-to-end test against the local app.
  • commit(message) Reversible write Local only. Allowed only when the feature's test passes.
  • ask_team(question) External Posts a question to the team. The agent moves to another feature while it waits.

No tool marks a feature done. The runtime flips a feature's status after its test passes.

Design decisions
DecisionThis design
Persistent stateIn the repo: features.json (each feature's test and status, written only by the runtime), PROGRESS.md (done, next, open questions, decisions), and git history as the checkpoint log. The runtime adds the session id, budget used, and the current feature.
MemoryA project instructions file: stack, commands, conventions, and team decisions such as "use the existing design system". Changes to it appear in the morning review, where people keep or revert them.
SubagentsA narrow yes. A reviewer with read-only tools checks each feature's diff against the spec before commit. An explorer handles large code searches. Only one agent writes code, which avoids conflicting edits.
Triggers and schedulingScheduled sessions every few hours during the day, plus sessions a person starts. A lease on the repo stops two sessions from running at once.
When things failA crash mid-change: discard uncommitted work and restart the feature from the last commit. A feature that fails in three sessions is marked blocked and raised to a person. Flaky tests get one rerun.
ApprovalsMerging to main happens in the morning review. Only people change the spec, the feature list, or the acceptance tests. New dependencies need approval.
Security boundaryA container with the repo and a local database of fake data. Egress to the package registry only. No production data or credentials. The acceptance tests and features.json are mounted read-only, so the agent cannot change what counts as done. The push token can push only the agent's branch.
Deterministic partsScheduling, the lease, the bootstrap steps, marking features passing from test results, commit rules, budgets, and the morning summary.
EvaluationPer feature: its test passes and the reviewer accepts. Per project: features passing over time, regressions, human rework time, and cost per feature. Before the real run, try a five-feature spec where you know the right result.

Alternatives

  • One endless conversation with compaction. Simpler, but each compaction can drop a decision, and a crash loses the thread.
  • A planner that turns features into issues for parallel workers. Faster when features are truly independent. When they touch the same files, you get merge conflicts.
  • People write the feature list and the tests, and the agent only implements. The most reliable split of the work.

What could go wrong

  • The agent declares victory with ten features still failing. Only tests change a feature's status. The run ends only when every feature passes or the budget runs out.
  • A new feature breaks an old one. Run every passing feature's test before each commit, or nightly if they are slow.
  • The progress file says done, but the code disagrees. Tests and git are the source of truth. The progress file is only a summary.
  • The agent edits an acceptance test so that it passes. The read-only mount makes that impossible.

Final scenario: migrate 300 repositories

This scenario does not match any chapter. That is the point. Your company is replacing an old logging library with a new one across 300 repositories owned by 40 teams. They use three languages, and some have unusual build setups. The new library has a different API. Log levels have new names, structured fields replace format strings, and the configuration file moves. The goal is a reviewed pull request in every repo within six weeks. CI must be green, and the log lines that alerts depend on must not change.

  1. How much of this is deterministic? Where does a model earn its place?
  2. What is the unit of work, and what state does each unit need?
  3. How do you avoid duplicate pull requests when jobs retry?
  4. What is the security boundary for building 300 repos you do not own?
  5. What counts as done for one repo? For the whole migration?
  6. Where do people approve, and how do you avoid swamping 40 teams?
  7. How do you test the approach before running it on all 300?
Reveal the rubric for this scenario

There is no single answer here. Grade your design with the table below, then with the general rubric after it. Many strong designs share one shape. A deterministic orchestrator works through a queue of repos. A codemod does the mechanical rewrite. An agent loop handles only what the codemod could not. Other shapes can score well if you argue their tradeoffs.

Traps in this scenario

  • A changed log format breaks alerts without any error. Find the log lines that alerts and dashboards query, and test them first.
  • Structured fields can log whole objects, including personal data that the old format string left out. Check what each new field contains.
  • Some repos call the logger through wrappers or helper functions. The codemod skips them, and a search for imports misses them.
  • Green CI is weak evidence in a repo with few tests. Spend more review effort where coverage is low.
  • Forty teams means forty review habits. A pull request that explains itself gets merged. A mystery pull request gets closed.

Systems analogy

This rubric is a production readiness review for agents. Like any readiness review, it asks about boundaries, failure, and monitoring before launch.

Where it breaks: a readiness review assumes components that behave the same way every time. Here one component may choose differently on every run. So each invariant must hold whatever the model chooses, and only code and the environment can promise that.

Invariants worth testing

The best designs state invariants you can test. These came up in almost every scenario above. Chapter 21 shows how to make an AI coding system prove them, and chapter 19 shows how to review code against them.

  • A rejected action never executes.
  • An approved action runs exactly as approved.
  • Every external effect has an idempotency key or a reconciliation step.
  • The model never sees a credential.
  • "Done" requires evidence that code checked.
  • Every run ends, on success, a budget, an error rule, or a person's stop.
  • State is saved before each side effect.

Takeaways

  • Most of these designs are workflows with one or two agentic steps. Agency goes where the next step depends on what the agent finds.
  • The model proposes. Code holds the side effects and the credentials.
  • Every external effect needs a gate, an idempotency key, or a reconciliation step.
  • "Done" means evidence that code checked, not a claim.
  • Evaluate on replayed real cases, several trials each, before anything goes live.
  • A design is ready to build when its boundary, approvals, and done criteria are specific.
