The design brief

Turn the course's target sentence into a brief that an AI coding system can build from, plus tests that show it did.

One sentence, many decisions

"Build an agent with isolated subagents, durable task state, filesystem tools, human approval for dangerous actions, context compaction, and persistent project memory."

Each phrase in this sentence sounds clear, but each one hides decisions. For example, "isolated subagents" does not say whether a helper may edit the same files as its parent. If you hand over the sentence as it stands, the AI coding system makes those decisions for you, usually without telling you.

Decode the sentence

Each phrase starts with an example from Patch, the course's coding agent, then a table of alternatives, failures, and what your brief must specify.

Isolated subagents

Patch needs to find every place that reads session tokens, which means opening about 40 files. Instead of reading them itself, it starts an explorer: a second agent loop with its own empty context and read-only tools. The explorer returns a 300-word summary, so Patch's context grows by 300 words instead of 40 files. "Isolated" names what the helper does not share with its parent: its context, its files, or its permissions. Chapter 7 covers the options.

Isolated subagents
AlternativesOne agent that keeps its own context small, or a loop in code that runs the same model call on each item.
What goes wrongA summary drops the detail that mattered, two helpers edit the same file, or cost grows because each helper builds its own context.
You must specifyEach helper's role, tools, and starting context, what it returns and how long, whether it shares files with the parent, and its budget.

How real systems do it

In Deep Agents (Python SDK 0.7.28), a child agent's conversation starts with only the task description. The parent gets back the child's final message. But by default the child reads and writes the same files as its parent, so its context is isolated while its files are shared. See chapter 17.

Durable task state

Patch's nightly run crashes at step 12 when the server restarts. The runtime saved a checkpoint, a snapshot of the run's state, after every step. So a new worker loads step 12 and carries on. Without checkpoints the run starts over, and it may repeat side effects, such as opening a second pull request. "Durable" means the run survives crashes, not that it runs for a long time. Chapter 12 covers checkpoints.

Durable task state
AlternativesShort runs that start over after a crash, which is fine when they have no side effects, or a workflow engine that records each step.
What goes wrongA resumed run repeats an action that already happened, two workers resume the same run, or new code loads a checkpoint that old code wrote.
You must specifyWhat a checkpoint holds and when code writes it, an idempotency key (an id the receiver uses to ignore repeats) for each external action, how to ask the receiver what happened when an outcome is unknown, and a lock so one worker owns each run.

Filesystem tools

Patch's test run prints 5,000 lines, far too many for its context. So the runtime saves the output to a file and shows Patch only the last 20 lines and the path. Patch reads more if it needs to. Filesystem tools are a few functions over one folder, such as read, search, edit, and write. They give the agent a place for everything that does not fit in context. Chapter 2 covers tools.

Filesystem tools
AlternativesA database behind narrow tools, a virtual folder kept in the agent's state, or a shell, which can do everything the file tools do and far more harm.
What goes wrongA path escapes the folder through ../ or a symbolic link, the agent overwrites a file it never read, or a huge file floods the context.
You must specifyThe root folder and what enforces it (the sandbox or path checks, never the prompt), which paths are read-only, and when a long read becomes a preview.

Human approval for dangerous actions

Patch wants to open a pull request. The runtime sees that open_pr is a gated tool, so it saves a checkpoint and stops. Then it asks a person to approve that exact call with its exact arguments. If the person approves, the runtime runs the call. If they reject it, the rejection goes back to Patch as the tool result. While the runtime waits, no model call is running. Chapter 11 covers the details.

Human approval
AlternativesBlock the action outright, run it in a sandbox where it cannot do harm, or let the other system enforce the rule, as branch protection does for a main branch.
What goes wrongA script reaches the same action by another path, people approve without reading because they are asked too often, or the call that runs differs from the approved one.
You must specifyWhich calls are gated, who approves and what they see, what happens if nobody answers, and that an edited call goes through the checks again.

Context compaction

After two hours, Patch's history fills 80% of its context window. The runtime asks the model to summarize the older messages and puts the summary in their place, so the run can continue. The full history stays in the runtime's log. The risk is the summary itself: if it drops "never edit the migrations folder", Patch may break that rule later. Chapter 4 covers compaction.

Context compaction
AlternativesShort runs that start fresh and keep notes in files, short placeholders in place of old tool outputs, or subagents that keep bulky work out of the main context.
What goes wrongThe summary drops a rule or a decision, a mistake in the summary becomes a fact, or frequent compaction wastes model calls.
You must specifyWhen compaction starts, what must survive word for word (the task, the rules, the decisions, the last test result), and whether code copies pinned rules back in afterward.

Persistent project memory

Every run, Patch used to rediscover that the project uses PostgreSQL and runs its tests with pytest -q. A project memory file stores facts like these, and the runtime adds the file to every call. Notes from past fixes live in a separate store, and the runtime retrieves them only when they match the task. Chapter 5 covers memory.

Persistent project memory
AlternativesA project instructions file that only people edit, a search of the repo and its docs when needed, or no memory at all for one-off tasks.
What goes wrongA fact goes stale when the code changes, text from a tool output gets saved and steers later runs, or the file grows until it crowds the context.
You must specifyWhat is always loaded and what is retrieved, who may write and whether the agent's writes need a person's approval, the scope, and a size limit.

What does this reduce to?

  • Isolated subagents = more loops, each with its own context and limits, returning short results.
  • Durable task state = a checkpoint after each step + idempotency for side effects.
  • Filesystem tools = a few functions over a bounded folder.
  • Human approval = a blocking gate in the dispatcher, bound to one exact call.
  • Context compaction = a rule for shrinking old context + a list of what must survive.
  • Persistent project memory = curated storage + a write policy + loading or retrieval.

A brief template

Give an AI coding system only the target sentence, and it will choose the step limit for you. It will also choose the compaction trigger and the list of gated actions. A brief lets you make those choices yourself. The template lists the sections where a guess does the most damage. One or two lines per section is usually enough.

Design brief template
SectionWhat to write
Goal and non-goalsWhat the agent is for, and what it must never do.
Users and triggersWho starts a run, and how: chat, schedule, event, or queue.
Loop and terminationThe loop's shape, what stops a run, and what proves success.
ToolsEach tool, its effect class, and where it runs.
State modelWhat the runtime tracks, where it lives, and when it is saved.
Context policyWhat each model call sees, in what order, and what stays out.
Memory policyWhat is remembered, who may write it, and how it is loaded.
PlanningWhether there is a plan or todo list, and who approves it.
DelegationHelper roles, their tools, what they return, and their limits.
SkillsWhich instruction packages exist, and when they load.
Security boundaryWhat the process can touch at all, and what enforces it.
ApprovalsEach gated action, who approves it, and what a rejection does.
DurabilityCheckpoints, retries, idempotency keys, and how a run resumes.
ObservabilityWhat each trace records, and where people read it.
EvaluationThe test tasks, what counts as success, and trials per task.
BudgetsSteps, tokens, money, and time, per run and per helper.

Write limits as numbers, such as "30 steps" instead of "a small budget", because code can check a number. For each rule, also say what enforces it: code, the sandbox, another system, or only the prompt. If only the prompt enforces a rule, the model can ignore it. And write "none" in sections that do not apply, so the AI does not invent something.

Systems analogy

A design brief works like a design document plus an interface contract: it says what to build and which rules must hold.

Where it breaks: a human engineer asks when something is unclear, but an AI coding system usually guesses and keeps going. So a brief must be explicit where a design document could stay vague.

Example: Patch's brief

Here is the template filled in for Patch. The numbers are examples, so choose your own, but do choose them.

Build Patch, a coding agent for our web service: a Python API on PostgreSQL, deployed on AWS, with a TypeScript front end.

Goal and non-goals

  • Fix bugs and make small changes, each delivered as a pull request with passing tests.
  • Never merge, deploy to production, or touch production data.

Users and triggers

  • Developers give tasks in the terminal. A nightly queue runs issues labeled patch-ok, one run per issue.

Loop and termination

  • Patch runs one agent loop with two helpers. The runtime stops when Patch proposes done and the checks pass, when a budget runs out, or after three identical tool calls in a row.
  • Done means the target test and the full test suite pass. The runtime checks this, not the model.

Tools

  • Read-only: search_files, read_file, and delegate, whose helpers can only read.
  • Reversible write: edit_file, which edits a clean checkout that git can restore, and todo_write, which edits the run's state.
  • Depends on the command: run_command, which runs only in the sandbox. Allowlisted commands such as pytest run without asking.
  • External: open_pr, run_migration(name) for the shared staging database, and deploy_staging(commit). The runtime runs each one outside the sandbox with its own narrow credential.
  • Outputs over 2,000 tokens go to a file, and Patch sees the last 20 lines and the path.

State model

  • One state object per run holds the messages, step count, files changed, test results, todos, approvals, cost, and pinned rules. The runtime saves it after every step.

Context policy

  • The order is system prompt, tool definitions, AGENTS.md, then history. Secrets never enter the context.
  • At 80% of the window, compact. Code copies the pinned rules back in after each compaction.

Memory policy

  • AGENTS.md holds the stack, commands, and conventions, and goes into every call. Up to three notes from past fixes are retrieved by file path and error text.
  • Patch proposes memory changes in its pull request, and a person accepts or drops them.

Planning

  • Patch keeps a todo list for tasks over about five steps. Changes to more than 10 files, or to the database schema, need an approved plan.

Delegation

  • Both helpers have read-only tools. The explorer returns under 300 words with file paths, and the reviewer checks the diff against the task and the test results.
  • Helpers cannot start helpers.

Skills

  • add-db-migration and deploy-staging load only when needed. Their steps end with the run_migration and deploy_staging tools, never with shell commands. Loading a skill grants no permissions.

Security boundary

  • Patch runs in a container with only the repo mounted and no credentials. Its network reaches only the package registry, so run_command cannot reach databases or deploy systems. The Git token, the migration credential, and the deploy token stay in the runtime, each usable by one tool.

Approvals

  • Gate open_pr, run_migration, deploy_staging, and deleting files outside the repo, a second line of defense behind the container. Each approval covers one exact call, and an edited call is checked again.
  • Interactive runs ask about commands outside the allowlist, and nightly runs reject them. A nightly run that reaches a gate saves a checkpoint and waits for a person.

Durability

  • After a crash, resume from the last checkpoint.
  • Open each pull request from one fixed branch per issue, such as patch/issue-4821. Uniqueness must come from the receiver, because two workers can both look, find no pull request, and both open one. So verify that the Git host refuses a second open pull request for the same branch.
  • If open_pr times out, its outcome is unknown. Look the pull request up by branch before trying again.

Observability

  • Record every model call, tool call, policy decision, and approval, and link the trace from the pull request.

Evaluation

  • Replay 50 past bugs, three trials each. A trial passes only if the tests pass and no gated action ran without approval. Track cost and human interventions.

Budgets

  • Each run gets 30 steps and $3, with 20 minutes when interactive and 60 minutes at night. Helpers get 15 steps each.

Acceptance: what to ask the AI to show you

Suppose the brief says that a rejected call never runs. Reading the brief cannot show that the code obeys it, and reading all the code is slow. So ask the AI coding system for three things.

  1. An enforcement map: for each rule in the brief, the file and function that enforce it. A rule with no entry is not enforced.
  2. Scenario tests with a scripted model, which is a fake model that returns replies you wrote in advance. The replies never change, so each test checks your runtime's rules, not the model's choices.
  3. A trace of one real run, such as fixing the failing auth test, so you can watch each rule act.
Scenario tests for Patch
RuleScenario test
Rejected calls never runThe model calls open_pr, and the test rejects it. Check that no request reached the Git server.
Approved calls run as approvedChange a call's arguments after approval. Check that the runtime asks again.
Retries do not duplicateRun two workers on the same issue, and crash one right after it sends open_pr. Resume it, and check that exactly one pull request exists.
The shell cannot deployFrom inside the sandbox, try to reach the staging database and the deploy service. Check that both connections fail.
Rules survive compactionPin "do not edit migrations/", then compact with a summary that drops everything. Check that the rule is in the next context.
Done needs evidenceThe model says "done" while the test fails. Check that the run is not marked successful.
Every run endsThe model repeats one call forever. Check that the run stops at the third repeat.
Helpers cannot writeThe explorer calls edit_file. Check that the call is rejected.
Secrets stay outGive the runtime a fake token, called a canary, that should never appear anywhere. Check that no recorded context contains it.
Resume skips finished workKill the worker mid-run. Check that the restarted run repeats no recorded tool call.

Also ask to see each test fail when its rule is removed. For example, if someone deletes the approval gate, the rejection test should fail. A test that still passes was never checking the gate.
