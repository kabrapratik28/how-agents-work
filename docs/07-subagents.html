Chapter 7 · Capabilities built on the loop

Subagents

Handing part of a task to a second agent loop keeps the main context clean and can save time. But some information gets lost on the way, and the extra loop costs tokens.

A subagent is another loop

Suppose Patch needs every place in the code that checks whether a login token has expired. Finding them means searching and reading about thirty files, but the answer is three lines. If Patch searches itself, all thirty files land in its own context and stay there.

Instead, Patch can call a tool named delegate with a short request. Behind that tool, your code starts a second agent loop with its own instructions, tools, and an empty history. When that loop stops, your code returns its final message to Patch as the tool result.

For the main agent, called the parent, this is an ordinary tool call. Only the inside of the tool is new: it runs a whole agent loop, called the child, instead of a function.

def delegate(call):                          # a tool, like read_file
    child = Agent(
        system=EXPLORER_PROMPT,              # its own instructions
        tools=[search_files, read_file],     # its own tools
    )
    report = child.run(call.args["objective"], max_steps=15)  # a whole loop
    return tool_result(call.id, report)      # the parent sees only this

What does this reduce to?

Subagent = a tool whose code runs another agent loop with its own context. The parent sees only what that tool returns.

Systems analogy

A subagent is like a spawned worker with its own context, such as a child process. You pass it arguments, it works in its own memory, and you get a return value back.

Where it breaks: a process gets its arguments exactly, but a subagent gets a paragraph of text that it can misread. Its return value is a summary written by a model, so it can leave things out or claim a success that never happened. And a separate context is not a separate machine, because the child can still change files the parent depends on.

What a subagent can change

A research agent might start one child per source, each with the same instructions and tools as the parent and a different brief. A coding agent might start a reviewer with its own prompt, read-only tools, and a cheaper model.

So "subagent" names a set of choices. The only fixed part is a separate loop with its own context, and everything else can match the parent or differ.

A single extra model call is not a subagent, because it runs once and returns. Examples are a summary, or the reflection call in chapter 6. A subagent loops, choosing its own steps until it stops.

The delegation contract

Suppose the parent writes the brief "look into the auth bug". The child starts with no history. It does not know which bug, which files the parent already read, or what answer is wanted. It will probably spend its budget rediscovering what the parent knew, then return a vague report.

A useful brief works like a contract between the two loops. It covers eight things:

brief = {
    "objective":   "List every place that checks token expiry. Do not fix anything.",
    "constraints": ["skip tests/fixtures", "all datetimes are timezone-aware"],
    "tools":       ["search_files", "read_file"],       # what it may do
    "output":      "path:line plus one sentence each, at most 900 tokens",
    "budget":      {"max_steps": 15, "max_tokens": 60_000, "timeout_s": 300},
    "owns":        ["notes/expiry-sites.md"],           # the only file it may write
    "cancel":      "the parent can stop it; notes written so far stay",
    "reconcile":   "the parent re-reads each line before editing it",
}

Some of these fields are only requests, and some can be guarantees. The objective and the output format are text, so the child may drift from them. But your code starts the child, so it can enforce the tools, the budget, and the files the child may write. For example, "do not edit files" in the brief is a request, while giving the child only read tools makes editing impossible.

In practice, the parent model writes the objective and the facts it knows as the arguments of its delegate call. Your code fills in the tools, the budget, and the owned files from a fixed template, so the model cannot loosen them.

What does this reduce to?

Delegation = a brief the parent model writes + limits your code enforces + a result the parent still has to check.

Call and return, or hand off

A support agent receives "I was charged twice." It could call a billing subagent, wait for its findings, and answer the customer itself. Or it could hand the whole conversation to a billing agent, which then talks to the customer directly.

The first pattern uses an agent as a tool: the parent calls it, waits for the result, and stays in charge. The second is a handoff: the first agent passes control to another agent and steps out.

Use call and return when the parent has to combine results or keep one voice toward the user. Use a handoff to route a conversation to a specialist. In a handoff, the conversation itself usually moves to the new agent, so it sees the history. A called child sees only its brief.

Context isolation, and its limits

In chapter 4, Patch's explorer read 31,000 tokens of code and returned a 900-token report. The parent's context grew by 900 tokens, not 31,000. That is context isolation: the child's reading stays in the child's context.

But isolation only covers what each model sees, not what each agent can change. People often blur four different arrangements.

What parent and child share
ArrangementWhat is sharedGood forWatch out for
Shared filesA folder or repoPassing big results by reference: write notes, return the pathTwo children editing one file

If children must not touch each other's files, give each its own copy of the work, such as a git worktree or a container.

How real systems do it

  • Deep Agents (0.7.28) isolates a child's context but not its files. With the default storage, children read and write the parent's files, and those files remain after the child finishes.

Specialization

Say a reviewer subagent has a prompt that says "you are a careful security reviewer". It also has no tool that can write, and only that second part is a guarantee. The prompt shapes what the reviewer tends to do, but the missing tools decide what it can do.

The cost is that a specialist knows less. For example, a reviewer that sees only the diff cannot tell whether the change matches the plan. Put what it needs in the brief. One loop can also specialize by switching its prompt and tools between phases. So you need a subagent only when you also want a separate context or budget.

Running children at the same time

Suppose three children take 2, 3, and 2.5 minutes. If the parent asks for all three in one reply, and nothing slows them down, they finish after 3 minutes. That is the time of the slowest one. One after another, they would take 7.5 minutes. This works like the parallel tool calls in chapter 2.

This saves time, but it does not save tokens. The extra tokens come from four places:

  • each child sends its own instructions and tool definitions on every one of its calls;
  • each child sends its brief on every call, too;
  • children re-read files the parent already knew, because they start empty;
  • and the parent makes extra calls to write the briefs and combine the results.

The time saving has limits too, because provider rate limits can make the children wait for each other.

Combining the results

In the simulator below, a child researching Redis reads a config file. It shows that the team's Redis server deletes old data when memory runs low. The child's short summary leaves that out. So the parent recommends Redis for a job queue, where losing jobs is a real problem.

This step, combining what the children send back, is called aggregation. Each result is a claim written by another model, not proof. Summaries drop details, and by the time the parent reads one, the child is usually gone. Results can conflict, and then the parent needs evidence, such as the original document or a test. A confident tone is not evidence, and neither is a vote. Reports also go stale: a child says "the test passes", then another child changes a file the test depends on.

So design what comes back:

  • Ask for references, such as file:line or a URL, so the parent can re-check claims cheaply.
  • Ask for risks as a separate field, because a free-form summary drops them first.
  • Have the child write full notes to a file it owns, and return the path.

Returning full transcripts instead would lose nothing. But the parent's context would fill up with everything every child read, which undoes the isolation you delegated for.

How real systems do it

  • Hermes (v0.22.2) returns each child's final text, cut at 24,000 characters, with the rest saved to a file. A task can carry an output schema. The parent checks the answer against it and sends one correction if it fails.
  • Deep Agents (0.7.28) returns one tool message holding the child's last reply. Its general-purpose child is told, "The calling agent only sees your final assistant message".

Children that start children

Suppose every agent may start three children, and each of those may start three more. Three levels then give you 3 + 9 + 27 = 39 agent runs. Each level also passes along a summary of a summary, so details fade. And one misread brief near the top sends a whole branch the wrong way.

So most designs cap it. The usual limits are a maximum depth, a maximum number of children, and one budget shared by the whole tree. Hermes and Deep Agents both keep depth at one level by default, because their children get no tool for starting more children.

def delegate(call, depth, budget):
    if depth >= MAX_DEPTH:
        return error(call.id, "delegation depth limit reached")
    share = budget.take(steps=15, tokens=60_000)    # the whole tree shares one budget
    tools = CHILD_TOOLS if depth + 1 < MAX_DEPTH else CHILD_TOOLS - {"delegate"}
    report = run_child(call.args, tools, share, depth + 1)
    budget.give_back(share.unused())
    return tool_result(call.id, report)

When multiple agents help

Four problems justify a subagent most often:

  • Independent parts. For example, three sources to research. Running them at the same time gets the answer sooner.
  • Noisy searching. Finding the answer means reading far more than the answer, and isolation keeps that reading out of the main context.
  • Different permissions. Part of the work should run with fewer rights, such as a read-only explorer.
  • A fresh review. A reviewer that never saw the author's reasoning judges the change itself.

Published numbers show both the gain and the cost. Anthropic reports one result from its research system. A Claude Opus 4 lead with Claude Sonnet 4 subagents outperformed a single Claude Opus 4 agent by 90.2% on its internal research eval. The same post says multi-agent systems use "about 15× more tokens than chats", and that "most coding tasks involve fewer truly parallelizable tasks than research".

A complex task is not, by itself, a reason. It often needs one agent with a better context, not several agents that each see only part of it.

When they cost more than they give

Skip subagents, or remove them, in these cases:

  • The parts are linked. Edits to the same files, or decisions that depend on each other, drift apart when made in separate contexts.
  • The task is small, so the briefs, the extra instructions, and the merging cost more than the work.
  • The parent needs the details that a summary would drop.

Pi takes the skeptical side on purpose and ships no subagents. Its creator, Mario Zechner, calls a built-in subagent "a black box within a black box". He calls parallel subagents building separate features "an anti-pattern in my book". His one approved use is code review, where a command starts pi again through bash.

So start with one agent. When you add a subagent, measure whether it helped (chapter 16), and check that the gain came from the extra agents (chapter 18).

Running example: Patch gets two helpers

Patch version 7 gets two subagents, both called like any other tool. The explorer searches the code and returns a short report with file:line references. The reviewer can only read files, and its brief carries the diff and the latest test results. Patch still makes every edit itself, in one context, because edits to the auth code depend on each other.

# Patch v7: two subagents, called like any other tool
+ explorer = Subagent(prompt=EXPLORE, tools=[search_files, read_file],
+                     output="at most 900 tokens, path:line refs", max_steps=15)
+ reviewer = Subagent(prompt=REVIEW, tools=[read_file],
+                     output="findings with path:line, no edits", max_steps=8)
+ tools += [delegate(explorer), delegate(reviewer)]

What goes wrong

The summary dropped what mattered

Why it happens
The child chooses what to report under a size limit, and a free-form summary keeps the headline but drops the warning.
How to spot it
The parent acts on a claim that has no reference, and later the child's notes show the missing fact.
What to do
Ask for risks as their own field, with references, and keep full notes in a file the parent can read.

Two children edit the same file

Why it happens
Each child follows its own brief and does not know the other exists, so the last write wins.
How to spot it
Two children's change lists touch the same file, or the tests pass for each child and fail after merging.
What to do
Let your code enforce which files each child may write. Or do linked edits in one agent, or give each child its own worktree.

Children disagree

Why it happens
They read different sources or misread the same one, and a wrong claim can sound as sure as a right one.
How to spot it
Compare the same field across reports, and flag contradictions before merging.
What to do
Settle it with evidence, such as the original source or a test. Chapter 15 goes deeper.

You decide, AI builds

Decide yourself

  • Whether a task needs a subagent at all.
  • Each subagent's tools, budget, output format, and writable files.
  • What parent and child share: files, data, the conversation, or nothing.
  • How the parent checks results before acting on them.

Delegate to AI

  • The delegate tool and the code that runs child loops.
  • Checking results against an output format, with one retry.
  • Counting tokens and steps across the whole tree.
  • Saving and linking each child's transcript.

Check yourself

What is a subagent, mechanically? (Q12)

Answer

A tool whose code runs another agent loop. The child has its own context and usually its own instructions, tools, and budget. The parent sees only what the tool returns.

When should you avoid splitting work across several agents? (Q13, Q14)

  1. When the subtasks are independent research questions
  2. When two parts of the work edit the same files
  3. When the search would flood the main context
Answer

When the parts are linked. Separate contexts make separate choices, and the last write wins. The other two are good reasons to use subagents.

Three children take 4, 6, and 9 minutes, and nothing slows them down. How long do they take at the same time, and one after another?

Answer

9 minutes at the same time, because the parent waits for the slowest child. 19 minutes one after another, because the times add up. The parent's own calls come on top in both cases.

Takeaways

  • Ask children for references and risks, and check their reports before acting on them.
  • Write the brief as a contract, and let your code enforce the tools, the budget, and the files each child may write.
  • Add a subagent only when you can name the problem it solves.
