Agent architectures

An agent architecture answers four questions: who decides the next step, how the work is split, what starts a run, and what survives a crash.

What an architecture is made of

So far, Patch is one loop that calls the model, runs tools, and repeats. Now suppose Patch must also fix CI failures at night and wait hours for a person to approve a database change. One loop in a terminal cannot do that, so you add parts around it: a trigger, saved state, or helper agents. How you arrange those parts is the architecture.

Every arrangement answers the same four questions:

  • Who decides the next step? Your code, the model, or a mix of both.
  • How is the work split? One loop, several workers, or a tree of managers.
  • What starts a run? A person, an event such as a webhook, or a schedule.
  • What survives a crash? Nothing, a saved plan, or a checkpoint after every step.

Single agent

The user asks Patch to fix a failing test. One loop does the whole job: Patch runs the test, reads the file, edits it, and runs the test again.

This is the easiest shape to build and debug, because one context holds every decision. But all the work shares that context, so long or messy work fills it up. Use it for open-ended tasks that fit in one context, which covers most coding tasks. Avoid it when big subtasks could run in parallel, or when the work must wait for hours.

Planner and executor

The user asks Patch to change how session tokens are stored. First, one model call (the planner) writes a numbered plan: pick a hash function, update the code that creates and checks tokens, and run the tests. Then a loop (the executor) carries out the steps, and a failed step sends the plan back to the planner.

A person can approve the plan before any file changes, and your code can save it and resume at step 3. But it costs an extra call, and a plan written before exploring is partly a guess. Use it for long tasks whose steps depend on each other, or for risky changes that need approval first. Skip it when each step depends on what the last one found, as in debugging (chapter 6).

Manager and workers

The user asks Patch to audit three services for code that still accepts an old token format. A manager agent splits the job into three parts and hands each part to a worker. Each worker is a separate loop with its own context and tools (chapter 7). The workers search at the same time and send back short summaries, which the manager combines.

This works well when the parts are independent, because the workers run in parallel and each context stays small. But the shape uses more model calls, and the summaries lose detail. The bigger risk is that workers cannot see each other's choices, so avoid this shape when the parts share decisions or files.

Published results show both sides. Anthropic's research system, a Claude Opus 4 lead with Claude Sonnet 4 helpers, beat a single Claude Opus 4 agent by 90.2% on Anthropic's internal research eval. But multi-agent systems like it use about 15 times the tokens of a chat. Anthropic also notes that most coding tasks have fewer truly parallel parts than research. Cognition argues for one agent by default: "Actions carry implicit decisions, and conflicting decisions carry bad results."

What does this reduce to?

A multi-agent system = several loops + a tool that hands a loop its task + a way to collect the results.

Hierarchical agents

Some jobs are too big for one manager. Say a team wants a long report on the health of its 40 services. A director splits the report into chapters for leads, and each lead splits its chapter into sections for workers. Results flow back up, and each level summarizes what it received.

A hierarchy can handle more work than one manager can track, because each level holds only its own part. But every level adds model calls and another summary that can drop a detail. A mistake at the top also spreads to everything below it. Use it only for very large jobs that split into areas. Many copies of one job, such as one change in 300 repositories, need a flat queue (chapter 20).

How real systems do it

  • Deep Agents 0.7 starts helpers through a task tool. Its default helpers do not get that tool, so they cannot start helpers of their own.
  • Hermes v0.22 uses a depth limit (max_spawn_depth: 1) that you must raise to allow deeper delegation.

Graph workflow

Suppose Patch handles every bug report the same way: research the code, plan a fix, make the change, and review it. A failed review sends the work back to research. When you know the steps, you can draw them as a graph, with boxes (nodes) for steps and arrows (edges) between them. Some nodes call the model, and others run plain code, such as the tests.

Graphs are predictable and easy to audit. Your code decides the known steps, so no model call is spent on them. It can also save progress, retry, or stop for a person at fixed points. But a fixed arrow cannot say "read one more file and try again", so graphs handle open-ended work badly. When one step is open-ended, make that node run an agent loop.

Event-driven agent

At 02:10, CI fails on the main branch and sends a webhook, an HTTP request that one service sends another when something happens. Nobody is awake to start Patch, so the webhook starts the run. A handler loads the saved state for that branch, runs the loop, and saves the state again. Between events, nothing runs.

This shape lets work start without a person, and a long wait costs nothing. The cost is that you now run a distributed system (chapter 12). Events can arrive twice, late, or out of order, so your code must save and load state correctly every time. Use it for agents that react to the world over days, such as CI fixers. When a person is waiting at the keyboard, an interactive loop is simpler.

The four choices underneath

The six shapes are not six options on one scale, because each one answers a different question. Event-driven is about what starts a run, and graph is about who decides the next step. Manager and workers, and hierarchy, are about how the work is split, and planner and executor keeps the plan as a separate object.

One combined architecture

Patch's unattended mode picks an answer to each question:

  • An event trigger, because nobody is at the keyboard.
  • A graph outside, because triage, fix, test, and pull request always come in that order.
  • An agent loop in the fix node, because the fix itself is open-ended.
  • Read-only helpers, because only one agent should write files.
  • A checkpoint after every node, so a crash or a long wait loses no work.

It has no planner, because each fix is small.

Systems analogy

Choosing between one agent and many is like choosing between a monolith and microservices. Splitting gives you isolation and parallel work, but you pay with partial failures and harder debugging.

Where it breaks: services talk through exact, typed contracts. Agents pass each other summaries in plain language, which lose detail, and each agent can misread its instructions.

Workflow patterns on the same map

Anthropic's guide "Building effective agents" (December 2024) names five workflow patterns. Each one fits the same four choices:

In the first three patterns, your code knows the steps before the run starts. In the last two, a model decides part of the flow while the task runs.

Why more agents can mean less reliability

Suppose a manager hands a job to three workers, and each worker gets its part right 90% of the time. If all three parts are required, the job works only when all three succeed:

one agent, one part              0.90
manager with 3 required workers  0.90 ** 3 = 0.73
director, 3 leads, 9 workers     0.90 ** 9 = 0.39   (counting workers only)

This math assumes that workers fail independently, that every part is required, and that nobody checks or retries. Anthropic's guide warns about the same effect: it lists "the potential for compounding errors" among the costs of agents.

Checks and retries make real systems do much better than the math. But failures with a shared cause, such as one bad instruction sent to every worker, fail again on every retry (chapter 15).

Choosing an architecture

Anthropic's guide recommends "finding the simplest solution possible, and only increasing complexity when needed." So start with one loop or a fixed workflow, and add a part only when the task gives you a reason:

Reasons to add a part, and parts to avoid
If the task hasAddAvoid
Open-ended steps that fit in one contextA single agent loopPlanners and workers that guess ahead
The same known steps every timeA graph, with code for the steps that need no modelAn open loop that rediscovers the steps on every run
Independent parts, or messy explorationWorkers, or a fan-out in code, that send back summariesOne context that holds every raw result
Parts that share decisions or filesOne agent that writes, with helpers that only readSeveral agents writing at once
Work that starts without a personAn event trigger and saved stateAn interactive loop
Long waits for approvals or peopleCheckpoints, so the process can end and an event can resume itA loop that waits in memory
A job too big for one managerA hierarchy, with checks at each levelOne manager buried in summaries

When the reason is real, extra parts can be worth their cost. In an Anthropic experiment, a single agent spent 20 minutes and $9 on a retro game maker that did not work. A harness with separate planner, generator, and evaluator agents spent 6 hours and $200, and its game worked. That task was long, and a separate evaluator could check the work.

Running example: Patch's architecture

Patch stays a single agent with two read-only helpers from chapter 7, an explorer and a reviewer. Only the main loop writes files, so related edits stay consistent. In unattended mode, that loop becomes the fix node of the graph above. Patch gets no hierarchy, because one agent can handle one bug.

- answer = run_agent(task, tools=TOOLS)

Design checkpoint 4: the expense agent

A 300-person company wants an expense agent. Employees forward receipts by email or upload a photo. The agent reads the receipt, checks it against the travel and expense policy, files the expense in the finance system, and routes it for manager approval. Employees can also ask it questions such as "why was my expense rejected?"

  1. Manager approval can take days. How does the work wait without a process sitting idle?
  2. The finance API times out after you sent "submit". What happens on retry?
  3. What triggers the agent: a schedule, events, or a user?
  4. Sketch the architecture. Single agent, graph workflow, or something else? Why?
  5. How do the parts communicate?
Reveal one reasonable design
  1. Save the expense's state as "awaiting manager" and end the process. Resume on the finance system's webhook or a scheduled check.
  2. Save an idempotency key, such as the receipt hash plus the employee, before the first attempt, and reuse it on every retry. If the finance API cannot check keys, look the expense up first and resubmit only if it is missing.
  3. All three: events (a new receipt, an approval webhook), users (questions), and a schedule (reminders).
  4. An event-driven graph: ingest, extract (model), validate (code), send exceptions to a person, submit (code, with the key), wait for approval, and notify. Questions go to a small agent with read-only tools.
  5. A database row per expense is the source of truth. A queue carries receipts and webhooks, and each model call sees only the current item.

Most of this design is a workflow. The model reads receipts, judges policy edge cases, and answers questions, and your code does the rest.

What goes wrong

Using many agents when one would do

Why it happens
Delegation looks advanced and is easy to add, so teams add it before the task gives them a reason.
How to spot it
Managers mostly pass summaries along, and the call count is several times that of one agent.
What to do
Run the same tasks with one agent and with helpers. Keep the helpers only if they win on success or cost.

Splitting work that shares decisions

Why it happens
A split by file or by function looks clean, but the parts often share a decision, such as a data format.
How to spot it
Edits fail to apply, tests fail only after merging, or the workers' reports contradict each other.
What to do
Give related changes one agent that writes, and let helpers only read and report.

Details lost in hand-offs

Why it happens
Each summary keeps what its writer thought mattered, so a constraint or an exact value can fall out.
How to spot it
Compare a worker's full output with what its manager received.
What to do
Ask for results with required fields, such as files touched and decisions made. Write details to files and pass the paths.

You decide, AI builds

Decide yourself

  • Which situations the system really faces: open-ended steps, independent parts, shared decisions, starts without a person, long waits.
  • For each part, whether your code or a model decides the next step, and which agent may write.
  • What starts a run, and what must survive a crash or a wait.

Delegate to AI

  • The graph code: nodes, arrows, and branch conditions.
  • Event handlers, queue consumers, and duplicate detection.
  • Saving checkpoints, resuming runs, and collecting results from workers.

Check yourself

Why use multiple agents? Name the situations that justify them. (Q13)

Answer

Independent parts that can run in parallel, exploration messy enough to flood one context, and parts that need different tools, such as a read-only reviewer. Each costs extra model calls.

Two workers edit different functions in the same file at the same time. What is the most likely problem? (Q14)

  1. Each worker runs out of context
  2. Their edits collide, or they make different choices for a decision both must share
  3. The manager forgets the original task
Answer

Each worker sees only its own part, so they can change the same lines or pick different formats.

An agent must start when a CI webhook arrives, fix the failing test, and then wait up to a day for review. How would you answer the four questions? (Q31)

Answer

Events start the run. A checkpoint before the review lets the process end until the review event resumes it. A graph runs the outer steps, and one agent loop does the fix.

Takeaways

  • Start with one loop or a fixed workflow, and add a part only for a reason you can name.
  • Split work across agents only when the parts are independent. Work that shares decisions needs one agent that writes.
  • Every hand-off adds model calls and another place to fail, so check results where they are handed over.
