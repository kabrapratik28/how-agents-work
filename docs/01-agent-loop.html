Chapter 1 · The core loop

The agent loop

Every agent repeats one cycle: build the context, call the model, do what it asked, record the result, and decide whether to go again.

Observe, decide, act, repeat

Robots and control systems have long been described by one cycle: observe the world, decide what to do, act, then look at the result. LLM agents run the same cycle.

Observe→ Decide→ Act→ Observe the result→ Repeat

Here is what each word means in an agent:

  • Observe: your code puts the current situation into the context, including the result of the last action.
  • Decide: the model reads the context and replies, either with an answer or with a request for an action.
  • Act: your code checks the request and carries it out.
  • Observe the result: your code adds what happened to the history.
  • Repeat: a loop in your code goes around again.

Only the decide step happens inside the model. Some models write out their reasoning before they decide, but that reasoning is part of the same reply. Between calls, nothing is thinking. Your code is just running.

What does this reduce to?

The agent loop = a while loop + build the context + one model call + run the requested tool + save the result.

Systems analogy

The loop works like an event loop that calls a remote service. Each time around, it sends a request to a service that keeps no state, gets back a decision, and acts on it. Your code is both the scheduler and the dispatcher.

Where it breaks: a normal event loop handles known event types with known handlers. Here the "event" is a decision written by a model in free form, so your code must check it every time before acting.

  • The context gets longer with every call, because your code sends the whole history each time.
  • Each tool result carries the id of the request it answers, so the model can match results to requests.
  • In the dangerous-action run, the rule that blocks the request lives in your code, not in the prompt. A person decides, and the run continues from a saved checkpoint.

How a run ends

Say the agent edits a file and replies, "Done, the test passes now." Should the run end? Usually yes, but only after your code checks that the test really passes. A good agent has several ways to stop, and you choose them on purpose:

  • The model says it is done. It replies without asking for a tool, or it calls a special "finish" tool.
  • A limit runs out. Your code caps the number of steps, the tokens, the cost, or the time.
  • A check passes or fails. For example, your code runs the tests. Some agents refuse to accept "done" until the check passes, and reply to the model with "The tests still fail. Keep going or explain why."
  • Errors pile up. The same tool keeps failing, or the model repeats the same request, so your code stops or asks a person.
  • A person stops it. The user cancels, or rejects an action.

Here is a sketch of those rules in code:

def should_stop(state, reply):
    if state.user_cancelled:             return "stopped by the user"
    if state.step >= state.max_steps:    return "step limit reached"
    if state.cost >= state.max_cost:     return "cost limit reached"
    if state.repeated_calls(window=3):   return "stuck: repeating itself"
    if not reply.tool_calls:                  # the model says it is done
        if state.success_check():             # confirm with evidence
            return "success"
        state.add_note("Check failed: " + state.check_output)
    return None                               # keep going

Notice the order. The hard limits come first, so a model that keeps saying "done" while the check fails still cannot run forever. Then a reply without a tool request leads to a check, not straight to success. That is the split from chapter 0: the model says it is done, your code stops, and a check confirms it.

How real systems do it

  • Pi (1.3.0) keeps going while there are tool requests or queued user messages, and has no step limit. If a reply was cut off at the output limit, it does not run that reply's tool requests, because their arguments may be incomplete.
  • Hermes (0.22.2) can send a reply back to the model when the model announces an action but never requests a tool. It has no step limit by default. Instead, a watchdog stops a run that makes no progress for 600 seconds.

Example: why long runs get expensive

Your code sends the whole history on every call, so the total cost grows faster than the number of steps. Suppose the fixed part of the context is 3,000 tokens, and each step adds 1,000 more.

call 1 sends   3,000 tokens
call 2 sends   4,000 tokens
call 3 sends   5,000 tokens
...
call 20 sends 22,000 tokens

total over 20 calls:
  20 x 3,000 + 1,000 x (0 + 1 + ... + 19)
= 60,000 + 190,000
= 250,000 tokens

So twenty steps cost a quarter of a million tokens, and doubling the steps roughly quadruples the cost. Prompt caching makes the repeated part cheaper, but the context still fills up. Chapter 4 shows what to do about that.

Other shapes of the loop

The basic loop has a few common variations. They differ in who decides the next step and in how the work is split up. This is a first look; chapter 14 covers them in depth.

Simple loop

LLM→ tool→ LLM→ tool→ LLM

This is the loop from the widget, often called a ReAct loop. The model picks every step. Start here. It handles a wide range of tasks when the tools and the stopping rules are good.

Event-driven agent

Here the loop runs once for each event, such as a new chat message, a webhook, or a scheduled time. The agent loads its saved state, runs the loop, and saves the state again.

def on_event(event):
    state = store.load(event.thread_id)    # what we knew before
    state.add(event)
    run_loop(state)                        # the same loop as before
    store.save(state)                      # keep it for the next event

This fits agents that live for days and react to the world, such as support bots, inbox assistants, and scheduled jobs.

Graph or state machine

Here you draw the process as boxes and arrows. Some boxes call the model, and some arrows depend on a check or on the model's choice. For example: research, then draft, then review, then either revise or publish.

Research→ Draft→ Review→ Revise or publish?

This fits when you already know the shape of the process. You get a natural place to save progress after each box, and a natural place for a person to approve.

Planner and executor

One model call writes a plan, and a loop carries out the steps. If a step fails, the planner revises the plan. This helps with long tasks where steps depend on each other, or when a person should approve the plan first. Chapter 6 covers when planning helps.

Parent agent with subagents

One of the parent's tools starts a second agent loop with a fresh context. The second loop does a focused job and returns a short result. This helps with independent research in parallel, and with keeping messy exploration out of the parent's context. Chapter 7 covers the costs.

Who decides what happens next?

Each shape gives a different answer to this question. At one end, your code decides every step and the model fills in blanks: that is a workflow. At the other end, the model decides every step within a few hard limits: that is an open agent.

Put each decision where the knowledge is. If you know the process, write it in code or as a graph. If the next step depends on what the agent discovers, as when debugging, let the model choose. Hard limits such as budgets, permissions, and approvals always stay in your code.

What goes wrong

The loop never ends

Why it happens
The tool results do not change what the model decides, so it repeats itself. Or nothing tells it what finished looks like.
How to spot it
Count the steps, and flag the same request with the same arguments appearing again.
What to do
Set step and cost limits, detect repeats, and state clearly what success looks like. Chapter 15 goes deeper.

The loop ends too early

Why it happens
The model says it is done before the work is finished, and your code treats that as success.
How to spot it
Run the success check every time the model says it is done.
What to do
Accept "done" only with evidence. Send a failed check back to the model.

Costs grow quietly

Why it happens
Every call sends the whole history again, so long runs cost far more than short ones.
How to spot it
Track tokens for the whole run, not only for single calls.
What to do
Set budgets, trim large tool outputs, and shorten old history. Chapter 4 explains how.

You decide, AI builds

Decide yourself

  • How a run ends: what counts as success, and which limits apply.
  • What happens when the model says it is done but the check fails.
  • Which shape of loop fits the task.

Delegate to AI

  • The loop itself, the step counter, and the timers.
  • Detecting repeated requests.
  • Counting tokens and cost, and logging every step.

Check yourself

What is the agent loop, in one sentence? (Q2)

Answer

A loop in your code that builds the context, calls the model, runs any tools the model asks for, adds the results to the history, and repeats until a stop rule fires.

The model replies without asking for a tool. What should a careful agent do?

  1. Report success, because the model is done
  2. Check the success criteria, and send the model back to work if they fail
  3. Call the model again with the same context
Answer

The reply only means the model thinks it is done. Your code decides whether to stop, and success needs evidence.

A run starts with 2,000 tokens of context and adds 500 tokens per step. Roughly how many tokens do 10 steps send in total?

Answer

10 x 2,000 + 500 x (0 + 1 + ... + 9) = 20,000 + 22,500 = 42,500 tokens. The last call alone sends 6,500.

Takeaways

  • Observe, decide, act means: build the context, call the model, run the tool, record the result. Only "decide" happens in the model.
  • Give every run several ways to stop: the model's "done" (checked against evidence), limits, error rules, and a person.
  • Because the history is sent on every call, cost grows much faster than the number of steps.
