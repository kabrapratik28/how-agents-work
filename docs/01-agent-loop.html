Chapter 1 · The core loop

The agent loop

Every agent runs the same cycle: build a context, call the model, carry out what it asked for, record the result, and decide whether to go again.

Observe, decide, act, repeat

The classic description of an agent comes from robotics and control systems. Observe the world. Decide what to do. Act. Observe the result. Repeat.

Observe→ Think and decide→ Act→ Observe the result→ Repeat

For an LLM agent, each of those words maps to something concrete. Only one of them happens inside the model.

  • Observe means the runtime builds a context from its state, including the latest results.
  • Think and decide is one model call. The output is either a final answer or a structured request for an action.
  • Act means the runtime checks the request and executes it against a tool or the outside world.
  • Observe the result means the runtime records what happened as a new message in its state.
  • Repeat is a condition in a loop, written in ordinary code.

Where does the thinking happen? Only inside the model call. Many models now produce reasoning tokens before their decision. Those tokens are part of the response to that one call. Between calls, nothing is thinking. The runtime is just running code.

What does this reduce to?

The agent loop = while loop + context builder + one model call + a dispatcher that runs requested tools + an append to the history.

Systems analogy

The loop is an event loop around a remote procedure. Each iteration sends a request to a stateless service, gets back a decision, and dispatches it. The runtime is the scheduler and the dispatcher.

Where it breaks: a normal event loop dispatches known event types to known handlers. Here the "event" is a free-form decision written by a model. The dispatcher has to validate it every time.

Step through a run

Step through three runs below. Watch three things at each step: what the runtime holds, what the model sees, and who acts. Pay attention to the context panel between model calls. It goes empty, because nothing is running there.

Interactive widget. Without JavaScript, here is the run in text. The user asks Patch to fix a failing auth test. The runtime builds a context and calls the model. The model requests run_command("pytest tests/test_auth.py"). The runtime checks the request against the tool schema and its policy, runs it, and appends the failing output to the history. On the next call the runtime sends everything again, and the model requests read_file("auth/session.py"). After an edit and a passing test run, the model replies with no tool calls. The runtime stops the loop and checks the evidence: the last test run passed.

Three details from the widget matter for the rest of the course.

  • The context grows on every call. The runtime re-sends the whole history each time, because the model holds nothing between calls.
  • Every tool result carries the id of the call that requested it. That is how the model knows which result answers which request.
  • In the dangerous-action run, the policy check sits in the dispatcher. The model's request is blocked before anything runs. A person decides, and the run resumes from a saved checkpoint.

How a run ends

A loop without a good exit is a bug. A good agent runtime has several exits, and you choose them on purpose.

  • Natural stop. The model replies without tool calls, or calls a finish tool. This is the model proposing that it is done.
  • Budgets. The runtime caps steps, tokens, money, or wall-clock time. Hitting a cap ends the run, usually with a report of where it got to.
  • Success evidence. A check passes, such as a green test suite. Some runtimes refuse to accept "done" until the check passes. They reply to the model with something like "Tests still fail. Continue or explain why not."
  • Error policy. Several tool errors in a row, or the same call repeated, ends the run or escalates to a person.
  • Human stop. The user interrupts, or rejects an action and ends the task.

Here is what those exits look like as code. It is a sketch, not a framework API.

def should_stop(state, reply):
    if not reply.tool_calls:                    # the model proposes done
        if state.done_check():                  # verify with evidence
            return "success"
        state.add_note("The check failed: " + state.check_output)
        return None                             # push back, keep going
    if state.step >= state.max_steps:      return "step budget used up"
    if state.cost >= state.max_cost:       return "cost budget used up"
    if state.repeated_calls(window=3):     return "stuck: repeating itself"
    if state.user_cancelled:               return "stopped by user"
    return None                                 # keep looping

Notice the first branch. "The model replied without tool calls" leads to a check, not straight to success. That is the propose, stop, verify split from chapter 0, written as code.

How real systems do it

  • Pi (1.3.0) runs two nested loops. The inner one continues while there are tool calls or queued steering messages. The outer one restarts only for follow-up messages. There is no turn cap. If a reply was cut off at the output limit, its tool calls are failed rather than run, because their arguments may be truncated.
  • Deep Agents (0.7.28) uses LangChain's agent graph. A run ends when a reply has no tool calls, with a recursion limit of 9,999 steps. An optional beta middleware asks a grader to score the transcript when the model tries to stop. Its feedback goes back into the loop until the grader is satisfied.
  • Hermes (0.22.2) can push a plain-text reply back into the loop with "stop gates". One nudges the model when it announces an action but calls no tool. The step cap is unlimited by default. A 600-second no-progress watchdog and repeat-failure guards stop runaways instead.

Worked example: why long runs get expensive

Because the runtime re-sends the history, cost grows faster than the number of steps. Take a run where the fixed part of the context is 3,000 tokens, and each step adds 1,000 tokens of history. The numbers are illustrative.

call 1 sends   3,000 tokens
call 2 sends   4,000 tokens
call 3 sends   5,000 tokens
...
call 20 sends 22,000 tokens

total input over 20 calls:
  20 x 3,000 + 1,000 x (0 + 1 + ... + 19)
= 60,000 + 190,000
= 250,000 tokens

Twenty steps, a quarter of a million input tokens. The total grows roughly with the square of the step count. Prompt caching lowers the price of the repeated prefix. It does not shrink the context, and the window still fills up. Chapter 4 covers what to do about that.

Loop designs: a preview

The basic loop has a few common variants. They differ in two things: who owns the control flow, and how work is split. This is a first look. Chapter 14 covers architectures in depth, once tools, state, planning, and subagents are in place.

Simple loop

LLM→ tool→ LLM→ tool→ LLM

This is the loop from the widget, often called a ReAct loop. The model picks every step. Use it as the default. It handles a surprising range of tasks when the tools and the stopping rules are good.

Event-driven agent

Here the loop runs once per event. A chat message arrives, a webhook fires, a schedule ticks, or a file changes. The agent is a handler. State is loaded at the start of each event and saved at the end.

def on_event(event):
    state = store.load(event.thread_id)    # restore what we knew
    state.add(event)
    run_loop(state)                        # the same loop as before
    store.save(state)                      # persist until the next event

Use it for agents that live for days and react to the world. Support bots, inbox agents, and scheduled jobs fit this shape.

Graph or state-machine agent

Here you draw the process as nodes and edges. Some nodes call the model. Edges can be fixed, or conditional on code or on a model's choice. For example: research, then draft, then review, then either revise or publish.

Research→ Draft→ Review→ Revise or publish?

Use it when you know the shape of the process. It gives you checkpoints at node boundaries, human gates at known points, and runs you can audit.

Planner and executor

One model call writes a plan. A loop executes the steps. When a step fails, the planner revises the plan. Use it for long tasks with dependencies, or when a person should approve the plan before any action. Chapter 6 covers when planning helps and when it only adds overhead.

Parent agent with subagents

One of the parent's tools starts another agent loop. That loop has its own context and returns a short result. Use it for independent research in parallel, or to keep noisy exploration out of the parent's context. Chapter 7 covers the costs.

Who decides what happens next?

Every loop design answers one question differently: who decides the next step? At one end, code decides everything, and the model fills in blanks. That is a workflow. At the other end, the model decides everything inside a few hard limits. That is an open agent.

Good designs put the decision where the knowledge is. If you know the process, encode it in code or a graph. If the right next step depends on what the agent discovers, let the model choose. Debugging a failing test is like that. Hard limits, such as budgets, permissions, and approvals, always stay in code.

What does this reduce to?

"How agentic is it?" = how many control-flow decisions the model makes, compared with how many your code makes.

Running example: Patch gets a loop

Patch version 1 replaces you with the loop. It gets one tool, run_command, so it can run the tests itself. It stops when the model replies without tool calls, or after 30 steps.

# Patch v0: you were the loop
- suggestion = model([system, user(paste)])
# Patch v1: the runtime is the loop
+ answer = run_agent(task, tools=[run_command], max_steps=30)

Patch can now try a fix, run the tests, read the failure, and try again. It can also loop forever on a bad idea. The step budget is its only protection so far.

What goes wrong

The loop never ends

Why
Each result fails to change the model's next decision, so it repeats itself. Or nothing tells it what "done" looks like.
Detect
Count steps. Hash recent tool calls and arguments, and flag repeats.
Mitigate
Step and cost budgets, repeat detectors, and clear success criteria in the instructions. Chapter 15 goes deeper.

The loop ends too early

Why
The model replies without a tool call before the work is finished, and the runtime treats that as success.
Detect
Run the success check at every proposed stop.
Mitigate
Do not accept "done" without evidence. Send the failed check back to the model.

Costs grow quietly

Why
Each call re-sends the history, so total tokens grow with the square of the steps.
Detect
Track tokens per call and per run, not only per request.
Mitigate
Budgets, trimming large tool outputs, compaction, and prompt caching.

An agent where a workflow would do

Why
An open loop is easy to build, so it gets used for processes whose steps are already known.
Detect
The traces show the same sequence of steps on almost every run.
Mitigate
Encode the known sequence in code, and keep model choices for the parts that vary.

You decide, AI builds

Decide yourself

  • The exits: what counts as success, and which budgets cap the run.
  • What happens at a proposed stop that fails its check.
  • Which loop design fits: simple, event-driven, graph, planner, or subagents.
  • Which decisions stay in code, and which go to the model.

Delegate to AI

  • The loop itself, step counters, and timers.
  • Repeat detection by hashing tool calls.
  • Token and cost accounting.
  • Trace logging for every step.

Check yourself

What is the agent loop, in one sentence? (Q2)

Answer

A runtime loop that builds a context from state, calls the model, executes any tool calls it returns, appends the results to state, and repeats until a stop condition fires.

The model replies without any tool calls. What should a careful runtime do?

  1. Report success, because the model is done
  2. Stop the loop, or check the success criteria first and push back if they fail
  3. Call the model again with the same context
Answer

A reply without tool calls is a proposal. The runtime decides whether to stop. Success needs evidence.

An agent answers customer emails as they arrive, over weeks. Which loop design fits best?

  1. A single simple loop that never exits
  2. An event-driven agent that loads state per email, runs a loop, and saves state
  3. A planner that plans all future replies up front
Answer

Event-driven. Each email starts a run with restored state. Nothing needs to stay running between emails.

A run has a fixed context of 2,000 tokens and adds 500 tokens per step. Roughly how many input tokens do 10 steps cost in total?

Answer

10 x 2,000 + 500 x (0 + 1 + ... + 9) = 20,000 + 22,500 = 42,500 tokens. The last call alone sends 6,500.

Takeaways

  • Observe, decide, act maps onto: build context, call the model, execute, record. Only "decide" happens in the model.
  • Every tool result is tied to the id of the call that asked for it.
  • A run needs several exits: natural stop, budgets, success evidence, error rules, and human stop.
  • Re-sending history makes cost grow roughly with the square of the steps.
  • Loop designs differ in who picks the next step. Put the decision where the knowledge is.
